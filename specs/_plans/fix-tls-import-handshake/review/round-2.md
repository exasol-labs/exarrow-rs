## Feasibility

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: plan.md § Impact, bullets "With TLS, the 30-second TLS handshake bound starts ..." and "A TLS handshake failure now comes from ..."; plan.md task 4.1, third and fourth bullets; decision-log.md Decision [2] Consequences
- Issue: The plan assumes that a TLS handshake timeout reaches the caller as `HTTP tunnel setup timeout after 30000ms (TLS handshake)`, and that an export returns the EXPORT statement's error only "when the statement fails first". `export_to_callback` awaits the statement first (`src/export/csv.rs:574-580`). When the statement fails, it aborts the tunnel task and returns `ExportError::SqlExecutionError`, whichever side failed first. When the TLS bound closes the tunnel and Exasol then fails the statement, as task 2.5 expects, the export never returns the `(TLS handshake)` text. A lock-wait export therefore fails with an Exasol SQL error, not with the message that the Impact bullet, task 4.1, and Decision [2] name.
- Fix: In plan.md § Impact and task 4.1, scope the `HTTP tunnel setup timeout after 30000ms (TLS handshake)` outcome to imports. State that an export returns the EXPORT statement's error whenever the statement fails, including after the TLS bound closes the tunnel, and returns the tunnel error only when the statement succeeds. Delete "when the statement fails first" in both places. In Decision [2] Consequences, replace "fails with a `TLS handshake` timeout on a healthy server" with "fails on a healthy server: an import with a `TLS handshake` timeout, an export with the EXPORT statement's error".

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: plan.md task 2.6, second test; task 2.1, peer modes; task 2.3, test change
- Issue: Three test steps rely on fake-peer hooks that `src/transport/test_support.rs` lacks. (a) The no-timer test "pauses the clock after the peer holds the magic packet, as `export_against_a_stalled_tunnel_setup` does". `FakeExasolServer::silent_after_handshake` sets `magic_packet_received: None`, and `wait_for_magic_packet` panics on it ("only silent_before_handshake reports the magic packet"). A pause before the client has read the EXA response lets auto-advance fire the 30-second EXA deadline instead of the TLS bound. (b) Task 2.3 asserts that the close-before-handshake peer "reads no new byte (it reads end of stream)", but task 2.1 defines that peer as one that closes the connection, so it cannot read afterwards. (c) "its listener accepts no second connection" needs a peer that keeps its listener and reports a second accept.
- Fix: In task 2.6, pause the clock only after the export is pending past `connect`: either wait 500 ms in real time first, as `test_export_to_callback_arms_no_timer_when_the_deadline_is_left_unset` does, or add a peer signal that fires after the peer writes the EXA response. In task 2.1, define the close peer as one that shuts down its write half after the EXA handshake and keeps reading. Add to task 2.1 that the stall peer and the close peer keep their listener and report whether a second connection arrives.

Other checks on this axis, no objection: every code reference in § Context matches the source, including `src/import/csv.rs:813-819`, `src/import/parallel.rs:42`, `src/export/csv.rs:531-596`, and the rustdoc at `src/export/csv.rs:429-438`.
