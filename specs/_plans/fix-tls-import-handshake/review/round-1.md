## Premortem

Six months from now this plan failed. Three stories explain why:

1. A user on a server version that task 1 never ran reports that `use_tls(true)` import hangs with no error. In 0.19.0 to 0.21.1 the same import failed after 30 seconds. The plan moved the start of the `TLS handshake` bound to Exasol's first TLS byte, and the wait for that byte has no bound, so a role or order mismatch now hangs. Routed to `[SCOPE_REDUCTION]` (Intent Fidelity).
2. A single-file CSV import with TLS hits a stalled handshake or a certificate alert. The import returns the TLS error, and the next statement on the same Connection fails with a stray IMPORT response. The TLS failure now happens after the IMPORT was sent, and `import_csv_internal` drops the in-flight statement on a tunnel error. Routed to `[NFR_IGNORED]` (Feasibility).
3. On `exasol/docker-db:2025.2.1` the TLS tests pass on unchanged code. `/speq:implement-pr` sees green suites and records deltas that describe a TLS server role the code never took. Separately, after PR #91 lands, `/speq:record` stops on a stale architecture BASE. Routed to `[HIDDEN_DEPENDENCY]` (Feasibility, one blocker and one advisory).

## Intent Fidelity

#### [SCOPE_REDUCTION] BLOCKER
- Location: decision-log.md § Design Decisions [2]; specs/_plans/fix-tls-import-handshake/import-export/http-transport/spec.md § "Tunnel setup fails with the step named when the peer stops answering" and § "TLS tunnel waits without a bound until Exasol starts the TLS handshake"; architecture.md § Constraints; plan.md task 2.3
- Issue: The request says "keep PR #89's 30 s `TLS handshake` bound as fallback". The recorded scenario bounds a peer that stops answering "after the EXA handshake and before it completes the TLS handshake". The delta narrows the bounded case to a peer that stops "after it sends the first bytes of the TLS handshake". Task 2.3 makes the tunnel wait "without a bound for the first byte with `TcpStream::peek`". If the fix's role or order assumption is wrong on a server version that task 1 did not test, neither side sends the first TLS byte. Under this plan that case hangs with no bound, which is the #53 symptom the fallback exists to catch. Today it fails after 30 seconds. Decision [2] gives a real reason for the change: Exasol can queue the statement or wait on a lock before its first byte. The choice is therefore between false `TLS handshake` timeouts and an unbounded hang. HUMAN: the choice changes what a user sees when the fix does not hold (an error after 30 seconds, or a hang), the requester named the fallback explicitly, and the headless run records no agreement to narrow it.
- Fix: Ask the requester to choose, and record the answer as an `## Interview` line in decision-log.md and in Decision [2]. Option A: keep a bound on the wait for Exasol's first TLS byte. Start the 30-second `TLS handshake` bound when the first tunnel read or write begins, so a peer that never starts the handshake fails with `HTTP tunnel setup timeout after <N>ms (TLS handshake)`. Then rewrite the two http-transport scenarios, the HTTP tunnel bullet of architecture.md § Constraints, task 4.1, and task 5.2. Replace `tls_tunnel_waits_past_the_setup_bound_for_the_peer_to_start_the_handshake` with a loopback test asserting that a peer that sends no TLS byte fails within the bound. Option B: keep the current design with the requester's explicit agreement. Add a sentence to the `Changed:` entry of task 5.2 stating that the tunnel no longer bounds a peer that never starts the TLS handshake.
- Escalation: HUMAN

Other checks on this axis, no objection: reproduction first on 2025.2.1 with 2026.1.0 if pullable (tasks 1.1 to 1.4). The not-reproduced branch is stated (task 1.6), and its mechanism is raised under Feasibility. The integration test fails, not skips, on a hang (task 1.2: `TLS_HANG_LIMIT` panics, and `skip_if_no_exasol!` panics under `REQUIRE_EXASOL`, which CI sets). One PR with a patch bump, the CHANGELOG `## <version>` section, Cargo.lock, and README are covered (tasks 5.1, 5.2). The Checklist runs fmt, clippy `--all-features`, `cargo test --lib`, and llvm-cov `--lib` with `strip_test_coverage.py check`, and never with `ffi`. Scope stays narrow: export coverage is justified in Decision [3], and task 3.4 is conditional.

#### [NFR_IGNORED] BLOCKER
- Location: plan.md § Impact, bullet "A TLS handshake failure now occurs after the statement was sent. An import returns it through the existing tunnel-error path ..."; plan.md § Implementation Tasks 2; `src/import/csv.rs` `import_csv_internal`
- Issue: After this change, a TLS handshake failure happens while the IMPORT statement is in flight on the Connection's transport. Examples are a stalled handshake and the certificate alert that task 3.4 anticipates. `import_csv_internal` returns `Err(e)` from the stream branch of its `select!` (`src/import/csv.rs:813-819`) and drops `sql_future` in the middle of `execute_query`. That future holds the transport lock taken in `make_sql_executor` (`src/adbc/connection.rs:1126-1144`). The native transport's `send_and_fill_buf` does not match responses to requests, so the IMPORT response, or part of a frame, stays unread, and the next statement on the Connection reads it. The single-file CSV path is the #53 path itself: `import_csv_from_file`, `import_csv_from_stream`, and the Arrow import through `csv::import_from_stream`. ADR `client-give-up-terminates-connection` says a client-side give-up "MUST terminate the connection and MUST NOT abandon the in-flight request". Before this plan, a TLS failure happened in `connect`, before the statement was sent, so it never reached this path. `finish_import` (parallel and Parquet paths) and `export_to_callback` await the statement first and are not affected.
- Fix: Add a task to group A before task 2.5. In `import_csv_internal`, when the stream future fails while the IMPORT statement is still running, await the statement before returning, then return the tunnel error. This is the rule `finish_import` already applies ("The task's own error wins if the task failed first"). Exasol fails the statement once task 2.3 closes the tunnel socket. Add a unit test with a mock `execute_sql` that completes only after the tunnel fails, and assert that the import returns the tunnel error after the statement future completed. Add a THEN line to the http-transport-tls delta scenario "TLS handshake starts after the IMPORT or EXPORT statement is sent": a TLS handshake failure returns the tunnel error only after the statement has returned. Correct the Impact bullet to name this path, and add `src/import/csv.rs` to group A's Knowledge.
- Escalation: MECHANICAL

#### [COMPLETENESS_GAP] ADVISORY
- Location: plan.md task 4.1 and § Impact; recorded `specs/import-export/csv-export-timeout/spec.md` § Background
- Issue: Task 4.1 tells users "a TLS handshake error is returned after the statement was sent". The recorded csv-export-timeout Background says the timer covers work "which all follow the tunnel setup". The docs paragraph that task 4.1 edits names `ExportError::HttpTransportError` and says "The driver has sent no IMPORT or EXPORT statement at that point".
- Fix: In task 4.1, state for each direction which error a TLS handshake failure returns: for import, the tunnel error; for export, the EXPORT SQL error when the statement fails first. Replace the error-type sentence of the "Tunnel Setup Timeout" paragraph for the TLS step, and state that `timeout_ms` now covers the TLS handshake. Add a DELTA:CHANGED block for the csv-export-timeout Background, or state in plan.md § Context why it stays.
