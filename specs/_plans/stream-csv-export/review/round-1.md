## Premortem

Six months from now this plan failed catastrophically. Why?

1. Compressed exports report the wrong error. A gzip or bz2 EXPORT fails on the server, for example through bad SQL, `query_timeout`, `KILL STATEMENT`, or a failed TLS handshake. Exasol closes the tunnel, the HTTP task ends and drops the sender, and `export_to_stream` calls `PieceDecoder::finish` on a truncated or empty stream. The consumer fails with `DecompressionError` before the SQL response arrives, so task 2.3 rule (a) returns `DecompressionError` instead of the Exasol error. Routed to `[REQUIREMENT_CONFLICT]` (Requirement Quality, first finding).
2. Callbacks that stop early fail on large exports only. A callback reads the first rows and returns `Ok`. The receiver drops, the HTTP task fails with `SendError`, the tunnel closes, Exasol fails the EXPORT, and rule (b) returns `SqlExecutionError`. An export that fits in 16 pieces still returns `Ok`. Routed to `[COMPLETENESS_GAP]` (Requirement Quality, second finding).
3. The plan lands on code it was not written against. The branch is 4 commits behind `origin/main`. After the rebase, recording the architecture delta reverts lines that #91 to #95 added, and task 1.2 names a TCP or TLS stream dispatch that `origin/main` replaced. Routed to `[HIDDEN_DEPENDENCY]` (Feasibility).

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: plan.md § Implementation Tasks 2.1
- Issue: Task 2.1 decodes gzip with `flate2::write::MultiGzDecoder`, which handles concatenated members, but bz2 with the single-stream `bzip2::write::BzDecoder`. The locked bzip2 0.5.2 has no write-side multi-stream decoder. After the first stream ends, its `write` returns `Ok(0)`, so a `write_all` inside `push` fails with `WriteZero`. Today's `read::BzDecoder` stops silently after the first stream instead. The plan does not state that Exasol writes one bz2 stream per export, and the 200,000-row integration test detects a second stream only if Exasol starts one at that size.
- Fix: State in task 2.1 that the plan assumes one bz2 stream per export, and make `PieceDecoder` start a new `BzDecoder` when bytes follow a stream end, as `MultiGzDecoder` does for gzip. Add the unit test `test_piece_decoder_decodes_concatenated_bzip2_streams`.

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: plan.md § Implementation Tasks 2.8
- Issue: Neither failure test names its query. The kill test relies on the statement still running when `KILL STATEMENT` arrives. If the body fits in the 16 channel slots plus the HTTP task's pending piece (about 1.1 MiB), the HTTP task forwards the whole body and sends 200 OK while the first write is held. The statement then completes before the kill, and the test fails for a reason outside the scenario. The writer test needs at least three pieces to fail on "its third write".
- Fix: In task 2.8, state that both tests export `large_export_query(rows)` from task 2.7 with a body larger than 17 pieces (the default 200,000 rows, about 10 MB, qualifies). State that the kill test asserts the export had not returned before it sent the kill.

## Requirement Quality

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: specs/_plans/stream-csv-export/import-export/csv-export/spec.md § "Export with compression", § "Export statement fails while data streams"; plan.md § Implementation Tasks 2.3 (a); decision-log.md [2] Consequences
- Issue: Two scenarios in this delta demand different errors for the same input. "Export with compression" says "IF the body ends before the compressed stream is complete, the export SHALL fail with `ExportError::DecompressionError`". "Export statement fails while data streams" says the driver "SHALL return `ExportError::SqlExecutionError`". A compressed export whose statement fails mid-transfer matches both. Task 2.3 makes the result depend on timing. When the statement fails, Exasol closes the tunnel, the HTTP task ends and drops the sender, `recv()` returns `None`, and `export_to_stream` calls `PieceDecoder::finish`. `finish` fails on a truncated stream: flate2 1.1.9 `write::GzDecoder` returns `corrupt()` when fewer than 8 trailer bytes arrived, and bzip2 0.5.2 `try_finish` returns `UnexpectedEof`. If the driver sees that consumer failure before the SQL response, rule (a) ("when the callback fails before the SQL response ... return the callback error") returns `DecompressionError`. An empty stream fails the same way. A compressed export whose statement fails before any data arrives (unknown table, server `query_timeout`, failed TLS handshake) can therefore surface `DecompressionError`. That breaks the recorded `import-export/csv-export-timeout` scenario "Server-enforced timeout governs an export", which requires `ExportError::SqlExecutionError`. `export_to_list` shows the same defect without compression when the body ends inside a quoted field or inside a multi-byte UTF-8 character (`CsvParseError`). The consumer cannot tell a clean end from a broken tunnel, because `DataPipeReceiver::recv` returns `None` in both cases.
- Fix: In plan.md task 2.3, add a rule before (a). When the callback fails and the HTTP task has already finished with an error other than `TransportError::SendError`, treat the failure as a broken tunnel: wait for the SQL response and return the SQL error, or the HTTP task error if the statement succeeded. The callback sees end-of-data only after the HTTP task has finished, so checking `http_task.is_finished()` at that point involves no race. In the csv-export delta, limit the `DecompressionError` step of "Export with compression" to a body that completed (zero-length terminator or full Content-Length) while the EXPORT statement succeeded. Add to "Export statement fails while data streams": "*AND* the driver SHALL return `ExportError::SqlExecutionError` also when the consumer fails because its data ended early, for example with `ExportError::DecompressionError`". State the new precedence in decision-log.md [2] Consequences. Add the loopback test `test_export_to_stream_returns_the_sql_error_when_a_gzip_tunnel_closes_mid_body`, in which the fake server closes after its first gzip chunk and the SQL double fails after the tunnel closed. Map the test in plan.md § Scenario Coverage.
- Escalation: MECHANICAL. Reading the two scenarios, task 2.3, and the recorded timeout spec settles it. The fix restores the recorded rule that the SQL error wins.

#### [COMPLETENESS_GAP] BLOCKER
- Location: specs/_plans/stream-csv-export/import-export/csv-export/spec.md § Scenarios; plan.md § Implementation Tasks 2.3, § Impact
- Issue: No scenario covers a callback that returns `Ok` before the transfer completes, for example one that reads the first rows and stops. Under task 2.3, the callback's return drops the receiver. The HTTP task then fails with `SendError`, as the http-transport delta requires ("IF the caller has closed its channel, client SHALL stop reading the body and SHALL fail the request"). The tunnel closes, Exasol fails the EXPORT, and rule (b) returns `SqlExecutionError`. A body that fits in the 16 channel slots still returns `Ok`, so the outcome depends on the size of the export. Today `export_to_callback` returns `Ok(r)` in both cases, because the callback runs only after the whole body was read and the statement returned. Neither plan.md § Impact nor the task 3.4 changelog entries mention the change.
- Fix: Add a `DELTA:NEW` scenario "Export callback returns before the transfer completes" to the csv-export delta. GIVEN a callback that returns `Ok` before the server completes the transfer, THEN the driver SHALL read and discard the remaining body without passing it to the callback, SHALL let the EXPORT statement finish, SHALL return the callback's value when the statement succeeds and `ExportError::SqlExecutionError` when it fails, and the connection SHALL remain usable. Implement it in task 2.3 without raising the 16-piece bound, and adjust the closed-channel step of the http-transport delta if the chosen mechanism needs it. Add the loopback test `test_export_to_callback_returns_the_callback_value_when_it_stops_before_the_last_piece`, with a body larger than 16 pieces, to plan.md § Scenario Coverage.
- Escalation: MECHANICAL. The fix keeps today's result for this case, so it needs no decision from the requester.

#### [AMBIGUOUS_REQUIREMENT] BLOCKER
- Location: specs/_plans/stream-csv-export/import-export/csv-export/spec.md § "Export applies backpressure to a slow consumer"; plan.md § Implementation Tasks 1.1, 2.1, 2.4
- Issue: The two THEN steps contradict each other and the planned design, so no pass or fail test follows from them. Step 1 says that when 16 pieces wait, "the driver SHALL NOT read further body bytes from the tunnel". Task 1.1 reads a piece first and then calls `sink.send(piece).await`, so it reads a 17th piece while 16 wait and only then blocks. Step 2 allows exactly that piece ("the one piece that it has read but not yet queued"), which step 1 forbids. Step 2 also caps the driver at 17 pieces, but the GIVEN includes "a writer that accepts no write". In that case `export_to_stream` (task 2.4) holds the piece it took from the channel, plus the `PieceDecoder::push` output for it, while `write_all` is pending. Task 2.1's `push(&mut self, piece: &[u8]) -> Result<Vec<u8>, ExportError>` copies the piece even for `Compression::None`. The driver then holds 18 pieces plus one decoded copy. Issue #59 is about SHALL lines that the code does not meet.
- Fix: Rewrite the two steps to match the design: "*THEN* the driver SHALL read at most one further piece from the tunnel until the consumer takes the next piece" and "*AND* the driver SHALL hold no more than the 16 waiting pieces, the one piece that it has read but not yet queued, and the piece that `export_to_file` or `export_to_stream` is writing, with its decoded output". State the same count in the architecture.md memory constraint. Change task 2.1 so that `push` takes the piece by value and returns it unchanged for `Compression::None`.
- Escalation: MECHANICAL. The scenario text and tasks 1.1, 2.1, and 2.4 settle it.

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: architecture.md § Data Flow (export bullet)
- Issue: The architecture delta says "export decompresses each piece when compression is set and passes it to a file, stream, or callback as it arrives". The csv-export delta "Export to callback" says "IF compression is configured, the pieces SHALL carry the compressed bytes as Exasol sent them". plan.md § Impact says "With compression, the chunks stay compressed, as before". The recorded architecture would state that callbacks receive decompressed data.
- Fix: In architecture.md § Data Flow, change the export bullet's tail to: "export passes each piece to a callback as it arrives, compressed as Exasol sent it, decompresses each piece when compression is set and writes it to a file or stream as it arrives, or collects all pieces for a list, Parquet, RecordBatches, or Arrow IPC; a full channel stops the tunnel read, so the server waits for a slow consumer". Keep the TLS handshake step that the `origin/main` version of this bullet has (see the Feasibility blocker).
- Escalation: MECHANICAL. Reading the two deltas settles it.

#### [AMBIGUOUS_REQUIREMENT] ADVISORY
- Location: specs/_plans/stream-csv-export/import-export/csv-export/spec.md § "Export consumer fails while data streams"
- Issue: The scenario says the driver waits for the EXPORT response "unless a configured `CsvExportOptions::timeout_ms` elapses first". The next step then says, without a condition, that the driver "SHALL return the consumer's error". The scenario does not say what the driver returns when the timeout elapses during that wait. The `timeout_ms` wrapper in task 2.3 returns `ExportError::Timeout { transport_terminated: true }`, as the recorded scenario "Explicit export timeout stops the export" requires, and drops the consumer's error.
- Fix: Add the step "*AND* IF `CsvExportOptions::timeout_ms` elapses before the EXPORT response arrives, the driver SHALL return `ExportError::Timeout` with `transport_terminated: true`, as `import-export/csv-export-timeout` specifies". Limit the consumer-error step to the case where the EXPORT response arrived.

#### [INFORMATION_LEAKAGE] ADVISORY
- Location: decision-log.md [1]; plan.md § Implementation Tasks 1.2, § Impact (Breaking bullet)
- Issue: Two public `HttpTransportClient` methods take `&tokio::sync::mpsc::Sender<Vec<u8>>`. The bounded tokio channel between the HTTP task and the consumer is an export decision (`DEFAULT_PIPE_BUFFER_SIZE` and `data_pipe()` in `src/export/csv.rs`). This plan also makes it part of the transport's public signature, so replacing the channel later is another breaking change. Decision [1] weighs only "keep buffering wrappers". It does not weigh a pull-based body reader on the transport, such as a method that returns the next piece and `None` after the terminator. That reader would keep the transport independent of the channel and leave the `send` to the export HTTP task.
- Fix: Add the pull-based body reader to decision-log.md [1] § Alternatives with the reason it lost, or adopt it in tasks 1.1 and 1.2 so that the helpers return pieces and the export HTTP task in task 2.3 sends them to the channel.
