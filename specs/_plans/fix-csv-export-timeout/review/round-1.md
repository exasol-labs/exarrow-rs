# Plan Review Findings: fix-csv-export-timeout (round 1)

## Summary
- Axes checked: 6/6
- Total findings: 16 (Blockers: 3, Advisory: 13)
- Intent Fidelity blockers: 0

This is round 1 of a fresh 2-round cap, reviewing the plan as revised after the maintainer's "Apply proposed fixes" on PR #54. Every artifact was re-read from scratch. `review/round-2.md` on disk describes the superseded cycle and is stale.

## Premortem

Three ways this plan fails six months out:

1. **A later plan deletes the export timer as a spec violation.** `/speq:record` merges the deltas. The permanent `connection-management/session-and-lifecycle` Background still reads "the driver SHALL NOT wrap query execution in a client-side timer", unscoped, while `export_to_callback` wraps `execute_query` in `tokio::time::timeout` on the `Some(ms)` arm. A future planner reads the Background, removes the arm, and reintroduces #52's inverse: an export nobody can bound. Routed to `[REQUIREMENT_CONFLICT]` — BLOCKER 1.
2. **Half the fix ships.** Group C runs 3.2 and 3.3 in parallel; both write `src/export/csv.rs`. One agent's write clobbers the other's. `cargo build` stays green for whichever survived, and tasks 4.3/4.4 then assert a `connection_terminated` field that is not there. Routed to `[TASK_GRANULARITY]` — BLOCKER 2.
3. **#52 reopens and CI never noticed.** A refactor writes `options.timeout_ms.unwrap_or(300_000)`. `test_csv_export_options_default` still passes (the field is `None`), task 4.1's ~13-second export still passes, and the only test that crosses 300 seconds is `#[ignore]`d behind an environment variable no Checklist command sets. Routed to `[TRACEABILITY_GAP]` — BLOCKER 3.

#### [SCOPE_CREEP] ADVISORY
- Location: plan.md § Implementation Tasks, task 3.3; csv-export delta § Scenario: No client-side export timeout by default, third `AND`
- Issue: task 3.3's justification is circular. The plan authors the spec bullet "the Arrow and Parquet export paths SHALL construct their CSV export options from these defaults", then adds a refactor task whose stated purpose is "makes the ... spec bullet observable, which it is not while `csv_options` stays a local". Issue #52 asks for none of it. The refactor does remove a real duplication — `src/export/arrow.rs:740-746` and `src/export/parquet.rs:759-765` are character-for-character identical — so it is defensible; but the plan should justify it as duplication removal inside the blast radius, not as service to a bullet the plan itself introduced. - Fix: In plan.md task 3.3, replace the "makes the ... spec bullet observable" clause with the duplication-removal rationale, and require the helper to take one `pub(crate)` struct with named fields (`column_separator`, `column_delimiter`, `host`, `port`, `use_tls`) instead of five positional parameters. #### [UNSTATED_ASSUMPTION] ADVISORY
- Location: decision-log § Design Decisions [3]; session-and-lifecycle delta § Scenario: Terminate a connection whose in-flight response is no longer trusted, second `AND`
- Issue: decision [3] justifies a new required public trait method by ADR `client-give-up-terminates-connection`, whose stated purpose is to "release the server session immediately instead of leaking it until idle-reap". But the spec bullet requires that `terminate()` "MUST NOT send a disconnect command and MUST NOT wait for any server response" — it drops the socket and tells the server nothing. Whether Exasol releases the session on socket close, or only at idle-reap, is never stated or verified anywhere in the plan. If it is the latter, `terminate()` satisfies the ADR's letter and not its purpose, and the plan has added a breaking public trait method for a benefit it does not deliver. No test in § Verification observes server-side session state.
- Fix: Add an `**Assumption:**` line to decision-log decision [3] stating that Exasol releases a session when the client socket closes, and mark it load-bearing for the ADR's stated benefit. Add a step to plan.md task 4.3 that opens a second connection after the terminating elapse and asserts the abandoned session is absent from `SYS.EXA_ALL_SESSIONS`, or add a § Manual Testing row that checks it by hand and record the observed reap behaviour.

#### [NFR_IGNORED] ADVISORY
- Location: plan.md § Impact, second paragraph
- Issue: Impact covers the async consequence of removing the default bound but never the synchronous wrappers. `Connection::blocking_export_csv_to_file` (`src/adbc/connection.rs:2065`) and its Parquet sibling run the export through `blocking_runtime().block_on(...)`. #### [AMBIGUOUS_REQUIREMENT] ADVISORY
- Location: plan.md § Implementation Tasks, task 3.2; csv-export delta § Scenario: Explicit export timeout stops the export, `THEN`
- Issue: this is the `ExportError::Timeout` shape the brief asked about. On the shape itself the bool is the right call and the plan should keep it: adding a variant would break every exhaustive `match` on `ExportError` in downstream code, whereas adding a named field breaks only exhaustive destructuring of one variant, and `Timeout { .. }` keeps compiling; the bool also keeps `timeout_ms` in one place instead of duplicating it across two variants; and the branch is an attribute of one outcome, not a second kind of error. Two defects remain. (a) **The field name contradicts the plan's own spec.** The spec bullet says the error reports "whether the driver terminated **the transport**", and the sibling scenario says "termination SHALL NOT change reported session state, so `Connection::is_closed()` still reports the session as open" — yet the field is named `connection_terminated`. A caller reading `connection_terminated: true` alongside `is_closed() == false` gets two direct contradictions from one API, and "use one term per concept" is violated between spec and code. (b) **The `Display` requirement is not writable as a pass/fail test.** Task 3.2 says "make the `Display` text state the outcome instead of hedging it" and "Update the display unit test at `src/export/csv.rs:849`" without giving the text. `thiserror`'s `#[error("...")]` takes one format string, so branching on a bool needs an inline conditional expression; an implementer has to invent both strings and the assertion.
- Fix: In plan.md task 3.2, § Impact paragraph 4, § Migration's last row, the Consequences table, the csv-export delta's `THEN` bullet, and decision-log decision [7] and finding [7], rename the field to `transport_terminated`. In task 3.2, specify both `Display` outputs verbatim — `Export timed out after {timeout_ms}ms; the transport was terminated, reconnect before the next operation` when true, and `Export timed out after {timeout_ms}ms; the transport is still usable` when false — so the unit test at `src/export/csv.rs:849` has a concrete assertion.

#### [COMPLETENESS_GAP] ADVISORY
- Location: csv-export delta § Scenario: Explicit export timeout stops the export, fourth `AND`
- Issue: the scenario specifies transport state on both elapse branches but says nothing about the caller's output. On the non-terminating branch the driver aborts `http_task` and drops the callback mid-stream, so `export_to_file` leaves a truncated file on disk, `export_to_list` returns no rows at all, and `export_to_stream` leaves the caller's writer holding a partial CSV, possibly a partial record. A caller cannot distinguish a timed-out export's output from a complete one, and there is no requirement to test against.
- Fix: Add one `AND` to the csv-export "Explicit export timeout stops the export" scenario: "*AND* the driver MAKES no guarantee that data already written to the caller's sink forms a complete CSV document, so the caller MUST discard partially written output after `ExportError::Timeout`." Add the same statement to plan.md § Impact paragraph 3 and as a § Migration row.

## Design Depth

No objection to the boundary itself — axis checked: `terminate()` is a genuine information-hiding boundary, because each transport owns how it abandons a socket and callers learn one method instead of two teardown sequences; making it required rather than defaulted is the right call, since a silent no-op default is exactly the failure decision-log finding [6] predicted; `export_to_callback` already depends on `TransportProtocol`, so calling `terminate()` there adds no new dependency direction and puts the obligation at the give-up site, which is where ADR `client-give-up-terminates-connection` places it.

#### [SHALLOW_DESIGN] ADVISORY
- Location: plan.md § Implementation Tasks, task 2.1, third and fourth sub-bullets
- Issue: two problems with how task 2.1 specifies the implementations. (a) The prescribed body — "drop the stream, clear the session, set the state to `Closed`" — is character-for-character the tail of the existing `close()` (`src/transport/native/mod.rs`: `self.stream = None; self.state = ConnectionState::Closed; self.session = None;`). The task does not say that `close()` should delegate, so one decision — how a transport tears down its local state — ends up owned in four places: `close()` and `terminate()` on each of two transports. That is the back-door duplication the shared mock's own module doc comment says this codebase exists to eliminate. (b) "Add a unit test asserting ... that the method performs no I/O" is not writable as a concrete pass/fail. `fn terminate(&mut self)` is non-async inside an `#[async_trait]` trait, so the signature already makes awaited I/O impossible, and there is no socket left to observe. An implementer asked for that test will either write a tautology or stall.
- Fix: In plan.md task 2.1, add to both implementation sub-bullets: "Put the local teardown in `terminate()` and have `close()` call it after its optional disconnect round-trip, so the teardown has one owner per transport." Replace "and that the method performs no I/O" with "The non-async signature is what forbids awaited I/O; state that in the trait doc comment instead of asserting it in a test."

#### [INFORMATION_LEAKAGE] ADVISORY
- Location: session-and-lifecycle delta § Scenario: Terminate a connection whose in-flight response is no longer trusted, fourth `AND`; decision-log § Design Decisions [7]
- Issue: the plan does not merely accept that `Connection::is_closed()` disagrees with transport reality — it freezes the disagreement into the permanent library as a normative requirement: "termination SHALL NOT change reported session state, so `Connection::is_closed()` still reports the session as open, and a caller MUST detect the termination from the failure of the next operation." One fact, this connection is dead, now has two owners that must disagree by spec. Decision [7] weighs exactly one alternative, mutating session state from six `Connection` entry points, and rejects it on cost. It never weighs the cheap one: `Connection::is_closed()` is a two-line `async fn` at `src/adbc/connection.rs:1053-1054` reading `self.session.is_closed().await`, and `self.transport` is an `Arc<Mutex<_>>` reachable from `&self`, so `self.session.is_closed().await || !self.transport.lock().await.is_connected()` is one edit in one method plus updating `is_closed_reflects_the_session_state` at `:3956`. Six call sites was never the only option, and a `SHALL NOT` in the library is far more expensive to undo than a bool on an error variant.
- Fix: Add the `is_closed()`-reads-the-transport option to decision-log decision [7]'s Alternatives with its real cost — one method, one unit test — and either adopt it or record a rejection reason that is not the six-entry-point cost. If rejected, downgrade the session-and-lifecycle fourth `AND` from a `SHALL NOT` to a non-normative note, so a future plan can fix `is_closed()` without amending the library.
