1. **Implementation stalls at the Group A seam, and the fix ships a dead method.** Task 2.1 lands the required trait method, the tree stops compiling, and neither Group B agent can produce a red test it can attribute to its own work. 2. **The non-terminating branch ships unverified.** Task 4.4 runs against a cold CI container, the 2-second bound expires during the EXPORT itself rather than in the callback, and the test fails asserting a usable connection against a terminated one. It gets quarantined as flaky, and the branch that round-1 blocker 3 was raised to protect has no coverage. Routed to Feasibility, `[UNSTATED_ASSUMPTION]`.

Retries succeed or hit a dead socket depending on which branch fired, and the driver knew the answer when it built the error. Routed to Requirement Quality, `[COMPLETENESS_GAP]`.

## Feasibility

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: plan.md § Implementation Tasks 4.4
- Issue: task 4.4's 2-second/5-second calibration has no margin for the SQL leg. The timer starts before `sql_task.await` (`src/export/csv.rs:486-488`), so the 2-second budget covers the tunnel connect, the EXPORT statement, the full tunnel read and the HTTP 200 before any of it is left for the callback. The mechanism does work as designed: `http_task` reads the whole body and sends it as one `tx.send(body)` (`src/export/csv.rs:452-469`) on a channel of `DEFAULT_PIPE_BUFFER_SIZE`, so it never blocks on the stalled writer, and `callback_task` is first polled only inside `tokio::join!` after `sql_task` completed. But on a cold container a first trivial EXPORT plus tunnel handshake exceeding 2 seconds is plausible, and then `sql_done` is still `false` when the timer elapses, the driver terminates, and the test asserts the opposite branch: its follow-up `conn.query("SELECT 1")` fails where the test expects success. Task 4.4 is the only coverage of the non-terminating branch, so a flake here quarantines the exact behavior round-1 blocker 3 was raised to protect.
- Fix: In plan.md task 4.4, raise the explicit bound to `.timeout_ms(10_000)` and the test writer's `poll_write` sleep to 30 seconds, and add one sentence stating why: the bound must exceed a cold-container EXPORT plus tunnel handshake so the elapse lands in the callback, and the writer stall must exceed the bound by a wide margin. State that the test performs one small throwaway export before the measured one, so the tunnel path is warm.

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: plan.md § Implementation Tasks 3.1 bullet 4; plan.md § Patterns row 6
- Issue: the plan states that the progress flag is "owned outside the timed block" but not the borrow region it has to survive. The elapse path needs two facts after the timed future is dropped: the flag, and that the outcome was `Err(Elapsed)` rather than an inner error. It also needs `&mut ws_transport` back to call `terminate()`, and `sql_task` holds `&mut *ws_transport` for the whole timed future (`src/export/csv.rs:472-479`). All three borrows end only when the `tokio::time::timeout(...)` temporary drops, which happens at the end of its enclosing statement. Writing `match tokio::time::timeout(dur, work).await { ... }` keeps the temporary alive across the arms and makes both the flag read and `ws_transport.terminate()` fail borrow-check; an implementer who hits that will be tempted to move `terminate()` inside the `map_err` closure, where the same borrow is still held. The plan gives no shape guidance for an `[expert]` task whose whole point is this sequencing.
- Fix: In plan.md task 3.1 bullet 4, state the required shape: bind the timeout result to its own `let` statement so every borrow taken by the timed future is released before the elapse handling runs, then read the flag and call `terminate()` after that statement. Add that the flag may instead be a `std::cell::Cell<bool>` borrowed immutably, which removes the conflict with the `&mut ws_transport` reborrow entirely.

## Requirement Quality

#### [REQUIREMENT_CONFLICT] ADVISORY
- Location: `specs/connection-management/session-and-lifecycle/spec.md` § "Query timeout"; `specs/_plans/fix-csv-export-timeout/connection-management/session-and-lifecycle/spec.md`
- Issue: the recorded library will carry two normative statements that a single reachable code path cannot both satisfy. The recorded "Query timeout" scenario ends "*AND* the driver MUST NOT wrap query execution in a client-side timer", with a GIVEN that includes "an explicit query timeout is configured via the `query_timeout=` connection-string parameter". A caller who sets `query_timeout=` on the connection and `timeout_ms` on the export puts `ws_transport.execute_query(&export_sql)` inside `tokio::time::timeout`, which is query execution wrapped in a client-side timer while that GIVEN holds. The plan argues the prohibition is scoped to `ConnectionParams::query_timeout` and `Statement::timeout_ms` (plan.md § Context bullet 1, decision-log.md decision [2] "Scope of the prior ADR"), and that argument is sound, but it lives only in artifacts `/speq:record` archives. The plan already edits this exact spec file, so the scoping never reaching the scenario is an omission rather than a cost.
- Fix: In `specs/_plans/fix-csv-export-timeout/connection-management/session-and-lifecycle/spec.md`, wrap the recorded "Query timeout" scenario in `<!-- DELTA:CHANGED -->` markers and narrow its last-but-one bullet to "the driver MUST NOT wrap query execution through `Connection::execute_statement()` in a client-side timer", then add one bullet stating that an explicit `CsvExportOptions::timeout_ms` bounds an export's combined SQL, transfer and callback and is outside this prohibition.

#### [REQUIREMENT_CONFLICT] ADVISORY
- Location: plan.md § Migration, last row
- Issue: the Migration table still states termination unconditionally: "Export timeout leaves the connection open and desynced | Export timeout terminates the transport; reconnect before the next operation". `import-export/csv-export/spec.md` bullets 3 and 4, plan.md § Impact paragraph 3 and § Consequences row 3 all say termination is conditional on the EXPORT response being unread. The Migration table is the row a CHANGELOG author and an upgrading caller read first, so the one artifact that states the old unconditional behavior is the one aimed at the audience that acts on it. Round-1 blocker 3's fix reached Impact but not Migration.
- Fix: In plan.md § Migration, replace the last row's New cell with "Export timeout terminates the transport only when it elapses before the EXPORT response is read; reconnect before the next operation in that case".

#### [COMPLETENESS_GAP] ADVISORY
- Location: plan.md § Implementation Tasks 3.2; `import-export/csv-export/spec.md` § "Explicit export timeout stops the export"; decision-log.md decision [7]
- Issue: a caller who catches `ExportError::Timeout` has no way to learn which branch fired. `ExportError::Timeout { timeout_ms: u64 }` (`src/export/csv.rs:67-68`) carries no discriminator, decision [7] deliberately leaves `Connection::is_closed()` returning `false` after termination, and task 3.2 resolves the gap with prose: extend the message "to state that the connection may have been terminated". The driver knows the answer at the moment it constructs the error, so "may have been" discards information the code holds. The specified recovery path, detect it from the next operation's failure, forces every caller to either reconnect defensively on a bound that fired during a slow callback or issue a probe statement whose failure is indistinguishable from any other failure.
- Fix: In plan.md task 3.2, add a `connection_terminated: bool` field to `ExportError::Timeout`, set it from the same flag that gates the `terminate()` call, and make the `Display` text state the outcome rather than hedge it. Add a bullet to the "Explicit export timeout stops the export" scenario in `import-export/csv-export/spec.md`: the returned `ExportError::Timeout` SHALL report whether the driver terminated the transport. Add the field to plan.md § Impact as a fifth breaking change and to the § Migration table.
