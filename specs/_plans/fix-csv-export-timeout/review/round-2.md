## Premortem

Three ways this plan fails six months out:

1. **The fix ships and nobody can use it for the case it was written for.** Task 3.1 prescribes `std::cell::Cell<bool>` as "the preferred shape" for the progress flag. `&Cell<bool>` is not `Send`, so the future returned by `export_to_callback` — and by every public `Connection::export_*` method that awaits it — becomes `!Send`. A user who writes `tokio::spawn(async move { conn.export_csv_to_file(...).await })`, the ordinary way to run an eight-minute export, no longer compiles. No in-repo code spawns an export, so `cargo build`, `cargo test`, and `cargo clippy` all stay green and no test in § Verification detects it. Routed to `[NFR_IGNORED]` — BLOCKER 1.
2. **Group B lands red and task 2.3 gets reverted to unblock it.** `MockTransport` is a `mockall::mock!` double, and no test in the crate calls `expect_is_connected`. Once `is_closed()` reads the transport, two existing unit tests panic on an unexpected mock call. Task 2.3 tells the implementer those assertions "still hold, since a live transport reports `is_connected() == true`", which is false for a mock. The cheapest unblock is `expect_is_connected().returning(|| false)`, which pins `is_closed()` to the old answer permanently. Routed to `[UNSTATED_ASSUMPTION]` — BLOCKER 2.
3. **The one test proving the terminating branch is quarantined.** Task 4.3 asserts the abandoned session is absent from `SYS.EXA_ALL_SESSIONS` immediately after dropping the socket, while roughly 19 seconds of cartesian product is still running server-side. If Exasol reaps on statement completion rather than on socket close, the assertion fails, the test that proves `transport_terminated: true` goes red for a reason unrelated to the branch, and the next maintainer deletes the check or the test. Routed to `[COMPLETENESS_GAP]` — ADVISORY.

#### [NFR_IGNORED] BLOCKER
- Location: plan.md § Implementation Tasks, task 3.1, fourth sub-bullet (plan.md:143); § Design → Patterns, "Progress flag owned outside the timed block" row; decision-log § Review Findings [9], Direction change
- Issue: task 3.1 prescribes `std::cell::Cell<bool>` for the progress flag — "A `std::cell::Cell<bool>` borrowed immutably removes that conflict outright and is the preferred shape." The flag is set inside the timed async block after `sql_task.await` and read outside it, so the async block captures `&Cell<bool>` and holds it across two await points. `&Cell<bool>` is `Send` only if `Cell<bool>` is `Sync`, which it is not. Compile-verified with `rustc --edition 2021`: a minimal future capturing `&Cell<bool>` across an await fails `assert_send` with `error[E0277]: Cell<bool> cannot be shared between threads safely ... required for &Cell<bool> to implement Send`, and rustc's own note recommends `AtomicBool`. Consequence: `export_to_callback` (`src/export/csv.rs:381`), `export_to_list`, `export_to_stream`, and every `Connection::export_*` method that awaits them return `!Send` futures. Those futures are `Send` today whenever the caller's callback and writer are — `export_csv_to_stream` bounds `W: AsyncWrite + Unpin` with no `Send` bound, so Send-ness is the caller's to keep. `tokio::spawn` of a long export is the canonical way to use the behavior this plan exists to enable, and it stops compiling. Nothing in-repo detects it: no `tokio::spawn` appears in `tests/`, `examples/`, or `benches/`, and `src/adbc_ffi.rs` uses `get_runtime().block_on(...)` throughout, which requires no `Send`. This is a silent seventh breaking change on a plan whose § Impact opens "This release breaks the public API in six ways."
- Fix: In plan.md task 3.1, fourth sub-bullet, replace `std::cell::Cell<bool>` with `std::sync::atomic::AtomicBool` and state the reason: `&AtomicBool` is `Send` and `&Cell<bool>` is not, so a `Cell` would make every public export future `!Send` and break `tokio::spawn` of an export. Specify `store(true, Ordering::Relaxed)` inside the timed block and `load(Ordering::Relaxed)` after it, since the flag crosses no thread boundary. Mirror the change in the § Patterns row and in decision-log finding [9]'s Direction change. Add a `--lib` unit test to task 3.1 and to § Verification → Scenario Coverage that pins the guarantee: `fn assert_send<T: Send>(_: T) {}` applied to the future returned by `export_to_callback` over a `MockTransport`.

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: decision-log § Design Decisions [7], Rationale, third sentence; plan.md § Impact, fourth paragraph
- Issue: the deadlock argument rests on a false premise — "`is_closed()` takes `&self` while every operation takes `&mut self`, which Rust already serializes." `Connection::shutdown()` also takes `&self` and locks the transport (`src/adbc/connection.rs:1090`, locking at `:1093`). The conclusion survives, because `tokio::sync::Mutex` is acquired without nesting on either path, so no deadlock exists. The stated reason does not, and it hides the real behavioral change: `is_closed()` goes from a session-state read that never waits to one that waits on the transport mutex. Every export holds that mutex for its whole duration — `export_csv_to_stream` locks at `:1321` and holds the guard across the `export_to_stream` await — and this plan removes the 300-second bound on how long that is. A caller using `is_closed()` as a cheap liveness probe now blocks for the length of an unbounded export. Neither § Impact paragraph 4 nor § Migration says so.
- Fix: In decision-log decision [7], replace the "every operation takes `&mut self`" clause with: "`shutdown()` is the only other `&self` method that locks the transport, and neither path nests the lock, so no deadlock is possible." Add one sentence to plan.md § Impact, fourth paragraph: "`is_closed()` now waits on the transport mutex, so a call made while an unbounded export holds it blocks until that export returns." Add a matching § Migration row.

## Design Depth

No objection to the boundary — axis checked: `terminate()` is a real information-hiding boundary, because each transport owns how it abandons a socket and callers learn one method instead of two teardown sequences; making it required rather than defaulted is correct, since a no-op default is the failure decision-log finding [6] predicted; and adopting the `is_closed()` fix removed the `SHALL NOT` that would have frozen one liveness fact into two owners required to disagree, which is a genuine improvement over the round-1 artifact.

#### [SHALLOW_DESIGN] ADVISORY
- Location: plan.md § Implementation Tasks, task 2.1, fourth sub-bullet (plan.md:135)
- Issue: "Implement it on the WebSocket transport in `src/transport/websocket.rs` with the same observable outcome and the same `close()` delegation" is written against the native transport's shape and does not transfer. Native `close()` ends in exactly the three lines the task names — `self.stream = None; self.state = ConnectionState::Closed; self.session = None;` — so extracting them into `terminate()` is clean. WebSocket `close()` has no such tail: it takes the stream inside a conditional (`if let Some(mut ws_stream) = self.ws_stream.take()`), sends a `CloseFrame`, drains messages in a `while let` loop bounded by `tokio::time::timeout(100ms, ...)`, and only then sets `self.state` and `self.session_info`. The field is `session_info`, not `session`, and the stream teardown sits mid-handshake rather than at the end. An implementer told to apply "the same delegation" must redesign that function unaided, on the half of the requirement whose unit test never executes in CI (`.github/workflows/ci.yml:255` is `--no-run`).
- Fix: In plan.md task 2.1, replace the WebSocket sub-bullet with the concrete shape: "`terminate()` sets `self.ws_stream = None`, `self.state = ConnectionState::Closed`, and `self.session_info = None`, sending no close frame and running no drain loop. `close()` keeps its close-frame handshake and drain loop, then calls `terminate()` in place of its final two assignments, so the teardown has one owner per transport."
