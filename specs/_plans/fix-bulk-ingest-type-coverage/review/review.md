# Plan Review Findings: fix-bulk-ingest-type-coverage

## Summary
- Axes checked: 6/6
- Total findings: 6 (Blockers: 2, Findings: 4)
- Intent Fidelity blockers: 1

## Ways This Plan May Fail

1. A user reads a table with an INTERVAL YEAR TO MONTH column through ADBC and ingests it back with `mode="replace"`. The values arrive as Interval(MonthDayNano) with a month component, so the type check passes, `DROP TABLE` and `CREATE TABLE` run, and the conversion then fails. The table is gone. That is the #111 defect in the newly supported type. Routed to Intent Fidelity `[INTENT_DRIFT]`.
2. CSV-path Parquet import of a Parquet INTERVAL column from a file without an `ARROW:schema` footer entry. arrow-rs reads the column as Interval(DayTime) and drops the month bytes, and the import stores wrong values without an error. Routed to Feasibility `[UNSTATED_ASSUMPTION]`.
3. A later change maps a new Arrow type in `arrow_to_exasol`. The native Parquet auto-create check of task 1.7 is a deny-list, so the new type passes native auto-create unverified. Routed to Design Depth `[INFORMATION_LEAKAGE]`.

## Intent Fidelity

#### [INTENT_DRIFT] BLOCKER
- Location: plan.md § Impact (bullet "Changed: an interval value that Exasol cannot store unchanged ..."); plan.md tasks 2.2 and 3.2; adbc-driver/bulk-ingestion/spec.md § "An Interval(MonthDayNano) value with a month component fails the ingest"; architecture.md § Constraints (the ADBC bulk ingest line)
- Issue: The interview answer is "Before any DROP or CREATE, so replace never drops the table and create never leaves an empty table (per #111)". The plan states the opposite for value errors: "ADBC ingest finds such a value, or a date outside Exasol's range, only after replace mode has dropped the table." With Interval support this case is common. Decision [4] Consequences states that "A value read from an INTERVAL YEAR TO MONTH column arrives as Interval(MonthDayNano) with a month component", which the recorded scenario `type-mapping/exasol-to-arrow-interval-hashtype` › "INTERVAL type mapping" confirms (YM holds 14 months). A read-then-replace round trip of such a table passes the type check, runs `DROP TABLE` and `CREATE TABLE` with `INTERVAL DAY(9) TO SECOND(3)`, and fails in the conversion. The old table and its rows are lost, and an empty table with a different column type remains. Create mode leaves an empty table for the same input. The order is not forced by the code. `bind` and `bind_stream` hold the whole input as one in-memory RecordBatch (src/adbc_ffi.rs:2266-2293). `import_from_record_batch` already converts the whole batch to CSV before it sends IMPORT (src/import/arrow.rs:563-564). Only the DDL in `execute_bulk_ingest` (src/adbc_ffi.rs:2136-2173) runs before that conversion, so converting first adds no memory or CPU. The month scenario covers Append only, so no scenario pins Replace or Create. The round-1 review accepted a docs warning for out-of-range dates as FINDINGS. The new interval rule turns that rare case into a routine one, so this round escalates it.
- Fix: (1) In plan.md task 2.2, append: "After the schema check, still before the connection lookup and any SQL, convert the bound batch to CSV bytes with `record_batch_to_csv` of `src/import/arrow.rs` and the `CsvWriterOptions` of `ArrowImportOptions::default()`, and map a conversion error with `to_adbc_error`. After the DDL, import those bytes through `Connection::import_csv_from_stream` (`src/adbc/connection.rs:1201`) with the CSV options that `csv_import_options` derives from the same `ArrowImportOptions`, so the batch converts once." In task 1.3, add "make `csv_import_options` `pub(crate)`". (2) In adbc-driver/bulk-ingestion/spec.md, rewrite the month scenario: GIVEN a table `T` with a column `I INTERVAL DAY(9) TO SECOND(3)` that holds one row, and no table named `NEW_T`; AND a RecordBatch with an `Interval(MonthDayNano)` column `I` holding 1 month, 0 days, and 0 ns; WHEN the RecordBatch is ingested into `T` with `IngestMode` `Append` or `Replace`, and into `NEW_T` with `Create` or `CreateAppend`; THEN each ingest SHALL fail with `AdbcStatus::Internal`, and the message SHALL name the month count and state that Exasol INTERVAL DAY TO SECOND has no month component; AND the driver SHALL send no SQL statement to Exasol for the ingest; AND `T` SHALL still hold its one row, and no table named `NEW_T` SHALL exist. (3) In task 2.3, add a unit test that ingests that value in every mode on a statement without a connection and asserts the conversion error, and add its row to § Scenario Coverage. (4) In plan.md § Impact, replace the sentence "ADBC ingest finds such a value, or a date outside Exasol's range, only after replace mode has dropped the table." with "ADBC ingest finds such a value, or a date outside Exasol's range, before its first SQL statement, so replace mode keeps the table." (5) In plan.md § Summary and in the architecture.md ADBC bulk ingest constraint, state that ingest checks the target catalog and every bound column type, and converts every bound value with the import CSV conversion, before its first SQL statement, so an ingest that these checks or the conversion reject drops, creates, and writes no table. (6) In task 3.2, delete the warning that a rejected value fails the ingest after replace mode has dropped the table. (7) In script M1, add a replace-mode ingest of the month value into `IV` and a final `SELECT COUNT(*) FROM PLAN_CHECK.IV` that prints `[(1,)]`, and update the expected lines and their count. (8) In decision-log.md, add Design Decision [5] "ADBC ingest converts values before its first SQL statement", with the rejected alternative "convert after the DDL, which drops the table in replace mode on a value error", and `Promotes to ADR: no`.

Other checks on this axis: no objection. Evidence: the Interval mapping in decision [4], the boundaries-and-validation delta, and task 1.1 matches the user's revised answer: YearMonth to INTERVAL YEAR TO MONTH, DayTime and MonthDayNano to INTERVAL DAY TO SECOND, failure for a month component, and no silent loss below a millisecond. Decision [2], task 2.2, and Impact apply one decimal limit in every mode, as the user decided. Tasks 2.1 and 2.3 and the two catalog scenarios implement the #109 answer. § Impact carries the adbc-drivers follow-up bullet. No task lacks a traceable user need.

## Feasibility

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: plan.md § Impact bullet 2 ("RecordBatch import, Arrow IPC import, and CSV-path Parquet import convert the same types"); architecture.md § Constraints (the interval line, "instead of dropping or rounding a part of the value"); decision-log.md [4]; plan.md tasks 1.5 and 1.7
- Issue: The plan assumes that the Arrow interval value it converts equals the value that the source holds. For CSV-path Parquet import this is false. In parquet-59.3.0, a Parquet INTERVAL column (FIXED_LEN_BYTE_ARRAY(12) holding months, days, and milliseconds) read without an `ARROW:schema` footer entry becomes `Interval(DayTime)`. See src/arrow/schema/primitive.rs:324-333, whose comment says "the results would be incorrect if all 12 bytes of the interval are populated". The DayTime reader decodes only bytes 4 to 12 (src/arrow/array_reader/fixed_len_byte_array.rs:236-242), so it drops the month part before the import CSV conversion sees the value. Today the CSV path fails on every Interval column, because `format_arrow_value` has no Interval arm. After tasks 1.3 and 1.5, a file whose writer stored no Arrow schema, holding an interval of 1 month, imports without error as `0 00:00:00.000`. This contradicts the plan's interval constraint and the user's "without silent data loss" direction. It also contradicts the recorded scenario `type-mapping/boundaries-and-validation` › "Lossless conversion validation" ("it SHALL warn or error on lossy conversions"). The native-path check of task 1.7 does not cover the CSV path. A test can reproduce the case: `ArrowWriterOptions::with_skip_arrow_metadata(true)` (parquet-59.3.0 src/arrow/arrow_writer/mod.rs:682) writes an Interval(YearMonth) column as a Parquet INTERVAL column without the hint.
- Fix: (1) Add task 1.9 to plan.md group A: "In `src/import/parquet.rs`, reject a field whose Arrow type is Interval when the Parquet footer's key-value metadata holds no `parquet::arrow::ARROW_SCHEMA_META_KEY` entry. Fail with `ImportError::SchemaInferenceError` that names the file and the column and states that the column would lose its month part. Run the check in `open_parquet_csv_reader`. On the CSV path with `create_table_if_not_exists`, also run it before `CREATE TABLE` in `import_from_parquet` and `import_from_parquet_files`, next to the task 1.7 check. Add a unit test that writes the file with `ArrowWriterOptions::with_skip_arrow_metadata(true)`, calls both functions with a closure that records every SQL statement, and asserts the error and an empty record." (2) Add a DELTA:NEW scenario to import-export/parquet-io/spec.md, "CSV-path Parquet import rejects an INTERVAL column from a file without an Arrow schema": GIVEN a Parquet file written without Arrow schema metadata, with the fields `ID` (Int64) and `X` (`Interval(YearMonth)`) holding 14 months; AND no table `T` exists; WHEN the application imports the file into `T` with `import_from_parquet`, `with_native_parquet(Some(false))`, and `with_create_table_if_not_exists(true)`; THEN the import SHALL fail with `ImportError::SchemaInferenceError` that names the column `X`, before the driver sends `CREATE TABLE` or `IMPORT`; AND `T` SHALL NOT exist. Add its unit and integration rows to § Scenario Coverage. (3) Add the rejection to plan.md § Impact, to the architecture.md interval constraint, and to the task 3.1 docs text. A simpler alternative is acceptable: reject Interval fields in every Parquet import, with the same scenario, Impact, constraint, and docs changes.

Other checks on this axis: no objection to the INTERVAL text format. Evidence: on the local `exasol/docker-db:2025.2.1` container, a CSV `IMPORT` accepted `5-03`, `-5-03`, `178956970-07`, `-178956970-08`, `2 12:50:10.123`, `-2 12:50:10.123`, `1 00:00:00.000`, `0 23:59:59.999`, and `-999999999 23:59:59.999` into `INTERVAL YEAR(9) TO MONTH` and `INTERVAL DAY(9) TO SECOND(3)` columns, with empty fields stored as NULL. The stored `-5-03` equals `CAST('-5-3' AS INTERVAL YEAR(9) TO MONTH)`. CSV `IMPORT` rounded `0 00:00:00.0005` to `.001` without an error, which justifies the sub-millisecond rejection. `CAST('1000000000 00:00:00.000' AS INTERVAL DAY(9) TO SECOND(3))` fails with "the leading precision of the interval is too small", which justifies the 999,999,999-day limit. `EXA_ALL_COLUMNS.COLUMN_TYPE` reads `INTERVAL YEAR(9) TO MONTH` and `INTERVAL DAY(9) TO SECOND(3)`, so the task 2.4 column type check is testable. The probe schema was dropped afterwards.

## Requirement Quality

#### [COMPLETENESS_GAP] FINDINGS
- Location: plan.md task 1.2
- Issue: Task 1.2 writes `i32::MIN` months as `-178956970-08`, and Exasol stores and returns that text (verified with CSV `IMPORT` and `SELECT` on 2025.2.1). `parse_interval_months` (src/types/conversion.rs:364-379) sums 178956970 × 12 + 8 = 2147483648 as a positive `i32` before it applies the sign, so `checked_add` fails and a query that reads the value fails. The recorded scenario `native-client/type-conversion` › "Direct binary to Arrow conversion for interval types" fails only "a month count outside the 32-bit signed integer range". After the plan, the driver writes the one in-range value that its own reader rejects. The task 1.2 round-trip assertion covers only the scenario values, which exclude `i32::MIN`.
- Fix: In plan.md task 1.2, add: "Make `parse_interval_months` compute the month count in `i64`, apply the sign, and convert it to `i32` with a checked conversion, so `-178956970-08` parses to `i32::MIN`. Include `i32::MIN` in the round-trip assertion."

Other checks on this axis: no objection. Evidence: the scenario values are consistent. 46_210_123 ms is 12:50:10.123, 63 months is `5-03`, 2_147_483_647 months is `178956970-07`, 1 day minus 1_000_000 ns is `0 23:59:59.999`, and `div_euclid(86_400_000)` maps -1, -86_400_000, and -86_400_001 ms to 1969-12-31, 1969-12-31, and 1969-12-30. Each new Background fact is used by a scenario step: the `EXA` catalog, no binary column type, DECIMAL precision 36, no month component, and leading precision 1 to 9. `speq plan validate` passes. Apart from the two conflicts raised above, no delta contradicts a recorded scenario in `adbc-driver/bulk-ingestion`, `type-mapping/arrow-to-exasol`, `type-mapping/boundaries-and-validation`, `import-export/arrow-recordbatch`, `import-export/arrow-recordbatch-dates`, `import-export/auto-table-creation`, or `adbc-driver/driver-interface`.

## Design Depth

#### [INFORMATION_LEAKAGE] FINDINGS
- Location: plan.md task 1.7; architecture.md § Constraints (the import CSV conversion line); decision-log.md § Review Findings "[plan-review] Native Parquet auto-create keeps rejecting the newly mapped types"
- Issue: Task 1.7 lists by hand the types that native auto-create rejects: Utf8View, Dictionary, BinaryView, FixedSizeBinary, and Interval. That list is the difference between what `arrow_to_exasol` maps and what was verified on the native path, so it repeats knowledge that `src/types/mapping.rs` owns. Because it is a deny-list, a type that a later change adds to `arrow_to_exasol` passes native auto-create unverified. That is the failure that decision [1] and the round-1 blocker describe. Nothing ties the list to `arrow_to_exasol`.
- Fix: In plan.md task 1.7, write the native check as an allow-list named once in `src/import/parquet.rs`. It holds the Arrow types that native auto-create accepted before this plan minus Interval: Boolean, the signed and unsigned integer types, Float32, Float64, Utf8, LargeUtf8, Binary, LargeBinary, Date32, Date64, Timestamp, Decimal128, and Decimal256. Every other field fails with the planned `SchemaInferenceError`. In the architecture.md constraint, state that native Parquet import with table creation accepts only the types it can load. Keep the six-file parquet-io scenario unchanged.

Other checks on this axis: no objection. Evidence: no decision-log entry sets `Promotes to ADR: yes`, so `[ADR_OVERPROMOTION]` does not apply. The 7 accepted ADRs are the placeholder lexer, zero-row result schema, batch arity check, query timeout forwarding, give-up termination, export timer, and Parquet export schema. None covers ingest, type mapping, or interval text, so `[ADR_CONFLICT]` does not apply. ADR-005's fail-fast check before any transport call agrees with the plan's direction. The delta BASE `af9b006de81e759c97524e6b69cae4091d9dac9c` equals `git hash-object specs/architecture.md`. A diff of the three CHANGED blocks against the current file shows only the import and types component lines, the ADBC C ABI line, and three added constraints. These match plan.md § Context, so `[ARCHITECTURE_DRIFT]` does not apply. The INTERVAL text writer sits next to `parse_interval` in `src/types/conversion.rs`, so one module owns the interval text format in both directions.
