## Data Flow

- connection URI -> Driver -> Database -> Connection::from_params -> native transport (default) or websocket transport (`transport=websocket`) -> Exasol: TCP or WebSocket connect, TLS, RSA-encrypted login that reports the client name and client version from ConnectionParams and the driver name `exarrow-rs` and, on the native transport, turns on the session attribute that makes Exasol send a TIMESTAMP WITH LOCAL TIME ZONE column with the `T_TIMESTAMP_UTC` wire type instead of the TIMESTAMP wire type, session info, all within one connection-timeout deadline that the transport starts in connect and spends in authenticate; then a schema from the URI goes to Exasol as the current-schema session attribute through set-attributes, and a schema that Exasol rejects closes the session and fails the connect
- Connection::set_schema or the ADBC `adbc.connection.db_schema` option -> TransportProtocol set-attributes -> Exasol -> get-attributes -> transport records the current schema that Exasol opened
- every Exasol response that carries the current-schema attribute -> native or websocket transport -> recorded current schema -> Connection::current_schema; an ADBC read of `adbc.connection.db_schema` asks Exasol with get-attributes instead
- SQL text -> Connection::execute_statement -> TransportProtocol::execute_query -> Exasol -> ResultSet: the native transport returns one Arrow RecordBatch per fetch, and the websocket transport returns JSON rows that query converts to RecordBatches with TypeMapper; on both transports, INTERVAL text becomes Interval(MonthDayNano) values through the one INTERVAL parser in types, GEOMETRY and HASHTYPE text becomes Binary values that hold the text bytes unchanged, and INTEGER and SMALLINT values become Decimal128(18, 0) and Decimal128(9, 0) values, which Exasol sends to the native transport as the `T_DECIMAL` and `T_SMALLDECIMAL` wire types, so these columns have the same Arrow data types and values on both transports; TIMESTAMP WITH LOCAL TIME ZONE values become Timestamp(Microsecond, "UTC") values on both transports, where the native transport holds the UTC instant that Exasol sends with the `T_TIMESTAMP_UTC` wire type and the websocket transport holds the date and time that the session time zone shows, so the two transports return equal values only in a UTC session; query builds the result set metadata schema from the column metadata with SchemaBuilder, which attaches each column's `exasol:` field metadata, and puts that field metadata on every batch of both transports, keeping the Arrow data types that the native transport decoded
- ResultSet -> ResultSetIterator::next_batch, awaited on the caller's runtime -> the batch of the execute response, then one TransportProtocol::fetch_results per call -> caller, which holds the only reference to each batch; the iterator closes the result set handle when it reports the end of the result set or a row count error, and ResultSetIterator::close closes it earlier; Connection::query and fetch_all collect all batches in memory and close the handle
- file, stream, or RecordBatch -> import -> http_transport handshake returns an internal address -> IMPORT SQL through the Connection transport -> with TLS, Exasol starts the TLS handshake on the tunnel as the client and checks the driver certificate against the `PUBLIC KEY` fingerprint -> Exasol pulls CSV chunks, or Parquet byte ranges on servers from 2025.1.11, through the tunnel; when the IMPORT SQL fails, import stops serving the tunnel and returns the error
- Parquet export source -> SELECT text -> TransportProtocol::create_prepared_statement -> result-set column metadata -> Arrow schema -> TransportProtocol::close_prepared_statement, all before the EXPORT SQL runs
- EXPORT SQL through the Connection transport -> with TLS, Exasol starts the TLS handshake on the tunnel as the client -> Exasol pushes CSV through the http_transport tunnel while the statement runs -> http_transport forwards the PUT body in pieces of at most 64 KiB through a 16-slot channel -> export passes each piece to a callback as it arrives, compressed as Exasol sent it, decompresses each piece when compression is set and writes it to a file or stream as it arrives, or collects all pieces for a list, Parquet, RecordBatches, or Arrow IPC; a full channel stops the tunnel read, so the server waits for a slow consumer
- ADBC driver manager -> AdbcDriverExasolInit or ExarrowDriverInit -> adbc_ffi -> adbc Connection on the 2-worker runtime -> RecordBatchReader returned over the C ABI
- ADBC `execute` of SQL with no bound RecordBatch that returns a result set -> adbc_ffi streaming reader, whose schema is the schema of the execute response batch -> each read blocks the calling thread on the 2-worker runtime for one ResultSetIterator::next_batch -> one batch over the C ABI; releasing the reader before its end blocks on the same runtime until ResultSetIterator::close has closed the result set handle; a bound RecordBatch, bulk ingest, and metadata calls such as GetObjects still return a reader over batches that adbc_ffi collected in memory
- ADBC database options `uri`, `username`, and `password` -> adbc_ffi at connection creation -> connection parses the URI once and merges the option credentials into ConnectionParams -> adbc_ffi keeps the ConnectionParams, never the URI string -> Connection::from_params on first use

## Constraints

- Rust edition 2021, and CI pins the stable toolchain
- Cargo feature `native` is the default transport, `websocket` is optional, `ffi` enables `native`, and a build without either transport rejects every connection
- Cargo feature `parquet` is off by default and is the only path to the `parquet` crate: Parquet import, Parquet export, and Parquet schema inference exist only with it, `ffi` does not enable it, and `benchmark` does
- TLS and server certificate validation are on by default
- Connection timeout defaults to 30 seconds and cannot exceed 300 seconds, and the driver has no idle timeout
- The connection timeout is one deadline that bounds the TCP connect, the TLS handshake, the WebSocket upgrade, and the login together, and its error names the step that ran out
- HTTP tunnel setup has two bounds of 30 seconds for every import and export, and the connection timeout changes neither: one deadline bounds the TCP connect and the EXA handshake together, and with TLS a separate bound covers the TLS handshake, starts at the first tunnel read or write, which can precede the IMPORT or EXPORT statement, and includes the wait for Exasol's first TLS byte, so time spent in the TCP connect and the EXA handshake does not shorten the 30-second TLS handshake bound; the opt-in CSV export timeout (`CsvExportOptions::timeout_ms`) starts after the EXA handshake, also covers the TLS handshake of a TLS export, and can elapse before the TLS bound with `ExportError::Timeout`; each tunnel setup error names the step that ran out
- A CSV export to a file, stream, or callback holds no more than 16 queued body pieces of at most 64 KiB each, the one piece that http_transport has read and not yet queued, and the piece that a file or stream export is writing with its decoded output, so its buffered body does not grow with the size of the export
- A native Parquet import from a file on disk reads each byte range from the file when Exasol requests it, in pieces of at most 64 KiB, so the file data it holds does not grow with the size of the file or of the range; a Parquet import from a stream holds the whole stream
- The native transport fetches up to the server's maximum data message size per batch, with a 64 MiB fallback
- The native transport runs the parameter set of a statement that returns an affected-row count as consecutive prepared-statement executions when one data message would exceed the server's maximum data message size, and each execution's data message stays within that size unless it holds a single row
- The FFI runtime is a multi-thread Tokio runtime with 2 workers so that import can run WebSocket and HTTP I/O at the same time inside `block_on`
- Native Parquet import requires Exasol 2025.1.11 or later, and older servers receive Parquet converted to CSV
- import has one conversion of Arrow values to CSV text, the import CSV conversion, which RecordBatch import, Arrow IPC import, ADBC bulk ingest, and CSV-path Parquet import share; TypeMapper maps an Arrow type to an Exasol column type only when the import CSV conversion converts the type, and the import CSV conversion also converts Decimal128 and Decimal256 with a precision above 36 or a scale outside 0 to the precision, for RecordBatch and Parquet imports into existing columns; native Parquet import with table creation accepts only a fixed list of field types that Exasol's Parquet reader is known to load, which excludes Utf8View, Dictionary, BinaryView, FixedSizeBinary, and Interval, and rejects every other field before CREATE TABLE, because on the native path Exasol's Parquet reader loads the values, not the import CSV conversion
- The import CSV conversion writes an Arrow interval value only when Exasol stores it unchanged: it fails on an Interval(MonthDayNano) value with a month component, on a day-time value with a fraction of a millisecond, and on a day-time value of more than 999,999,999 days, instead of dropping or rounding a part of the value; CSV-path Parquet import rejects an Interval field from a file whose footer holds no Arrow schema, before CREATE TABLE or IMPORT, because the Parquet reader then reads a Parquet INTERVAL column as Interval(DayTime) and drops its month part
- ADBC bulk ingest checks the target catalog and every bound column type before its first SQL statement, with one rule in every ingest mode: a column type needs an Exasol column type from TypeMapper and a conversion in the import CSV conversion, so an ingest that these checks reject drops, creates, and writes no table; ingest converts the bound values with the import CSV conversion after the DDL, so a value that the conversion rejects fails a replace-mode ingest after the old table is dropped and leaves an empty table in create mode
- Password encryption uses RSA PKCS#1 v1.5 through num-bigint because Exasol servers can send 1024-bit keys, which aws-lc-rs rejects
- Credentials are never logged or exposed, the Debug output of Connection, ConnectionParams, and ConnectionBuilder omits the password, and a connection URI parse error names the field, the query key, or the query parameter position, never repeats the userinfo or a query value, and names an unknown query key as written, so a password with an unencoded `?` can show a fragment in that error
- Runtime warnings go through the `log` crate facade, so the application's logger decides whether and where they appear
- Results stream as Arrow RecordBatches, and conversion is Arrow-native and zero-copy where possible
- A result set read through ResultSetIterator, or through the streaming reader that ADBC `execute` returns for SQL with no bound RecordBatch, keeps no batch that it has yielded: it holds the execute response batch until it yields it, and the batch of the fetch in progress, so its buffered rows do not grow with the size of the result; Connection::query, fetch_all, executions with a bound RecordBatch, and metadata readers hold every batch of the result
- CI rejects clippy warnings with all features, without the `parquet` feature, and in a websocket-only build, cargo-deny license findings, cargo-deny advisory findings in the dependencies of every Cargo feature, a failing library unit test with the `parquet` feature, the `websocket` feature, or the `ffi` feature, an integration test target that the integration job does not run, production line coverage below 80 percent, any file below 50 percent, and a failed SonarQube Cloud quality gate (intended to become a required check once rolled out)
- Library unit tests run in CI without a database server, so a unit test uses a test double, such as a mock transport or a local fake server, and never connects to Exasol
- The `ffi` unit tests run in CI outside the coverage run, because cargo-llvm-cov with the `ffi` feature deadlocks
- Integration tests require a running Exasol instance on port 8563, CI uses the `exasol/docker-db` image, and the CI integration job runs every integration test target under `tests/`
- DATE and TIMESTAMP values convert between Exasol and Arrow by the year, month, and day that Exasol reports, counted in the proleptic Gregorian calendar, on every read and write path
