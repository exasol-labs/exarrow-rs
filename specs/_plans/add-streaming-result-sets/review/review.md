# Plan Review Findings: add-streaming-result-sets

## Summary
- Axes checked: 6/6
- Total findings: 8 (Blockers: 1, Findings: 7)
- Intent Fidelity blockers: 0

Ways this plan may fail, routed into the taxonomy:

1. A Rust caller wraps the new async `next_batch` in `tokio::time::timeout` or `tokio::select!`. The dropped fetch leaves the transport out of sync, and the next statement on the connection reads the stale fetch response. Routed to `[ADR_CONFLICT]` (Design Depth).
2. A driver-manager caller runs another statement, a COMMIT, or a connection release before it drains a streaming reader. Before this plan, the reader held every row in memory. After it, the outcome is unknown or an error. Routed to `[COMPLETENESS_GAP]` (Requirement Quality).
3. The new KILL SESSION integration test races the server-side kill and fails intermittently. Routed to `[UNSTATED_ASSUMPTION]` (Feasibility).

## Feasibility

#### [NFR_IGNORED] FINDINGS
- Location: decision-log.md § Design Decisions [2] Consequences; plan.md § Implementation Tasks task 2.2
- Issue: Decision [2] accepts that "a read or a release from async code on a Tokio runtime panics". A release runs the reader's `Drop` inside the `extern "C"` release callback of the Arrow C stream. A panic cannot unwind out of that callback, so Rust aborts the process. The old `VecRecordBatchReader` release did no I/O and could not panic. The same `Drop` also runs while a thread unwinds from another panic, and a second panic there aborts too.
- Fix: In plan.md task 2.2, add: "In `Drop`, skip the blocking close when `tokio::runtime::Handle::try_current()` returns `Ok` or `std::thread::panicking()` is true, so a release never panics. The handle then stays open until the session ends." Add a unit test to task 2.1 that drops a streaming reader inside a `#[tokio::test]` body and asserts no panic and no `close_result_set` request. Add the test to the Scenario Coverage table. Change decision-log.md [2] Consequences so it states that a release in a runtime context skips the close.

#### [UNSTATED_ASSUMPTION] FINDINGS
- Location: decision-log.md § Design Decisions [3]; specs/_plans/add-streaming-result-sets/adbc-driver/result-schema/spec.md § Scenario "Reader schema is available before the first read"
- Issue: Decision [3] rejects `QueryMetadata::schema` because "its Arrow data types come from `TypeMapper`, which a native batch does not have to match". It assumes the execute response batch always carries the native types. That assumption fails when the execute response carries zero rows. In that case the native transport substitutes an empty batch (src/transport/native/mod.rs L369-373), and `ResultSet::from_transport_result` builds the first batch with `empty_record_batch(&schema)` from the TypeMapper schema (src/query/results.rs L188-193). For such a multi-fetch result, the reader schema is the TypeMapper schema that Decision [3] rejected, and the fetched batches carry the native types. The THEN step "every batch that the reader returns SHALL have the field names, the Arrow data types, and the field metadata of the reader schema" holds only if TypeMapper and native decoding agree for every Exasol type. Decision [3] says they need not agree, and no task checks it.
- Fix: Pick one option and write it into decision-log.md [3] and plan.md task 2.2. Option (a): state the assumption that TypeMapper and native decoding give the same Arrow data type for every Exasol type, cite the parity statement in the `specs/architecture.md` Data Flow, and correct the Rationale and Alternatives lines so they no longer claim the execute batch always carries the native types. Option (b): make the streaming reader compare the field data types of each fetched batch with the reader schema and fail that read with an error that names the field, then add a unit test to task 2.1 with a zero-row first batch and a fetched batch of a different Arrow type.

#### [UNSTATED_ASSUMPTION] FINDINGS
- Location: plan.md § Verification, Scenario Coverage row "A failed fetch fails the read of a streaming reader" (Integration)
- Issue: The test runs `KILL SESSION <id>` after the first read, and it asserts "that the failure arrives before all `MULTI_FETCH_ROWS` rows". The test assumes that the kill takes effect before the next fetch request. The native transport fetches up to the server's maximum data message size (64 MiB fallback), so the result of about 70 MB can need only one or two fetches after the execute response. If the kill is still in progress when the next fetch arrives, all rows can arrive and the assertion fails intermittently. The existing kill test in tests/import_export_tests.rs (L850-852) states that a kill takes effect only under some conditions, and it waits on the server with `wait_until_session_executes`.
- Fix: In the plan.md Scenario Coverage row, change the test description as follows. After `KILL SESSION <id>` returns, the second connection polls `EXA_ALL_SESSIONS` until the reader's session is gone, bounded at 30 seconds. Only then does the test read from the reader. Keep the assertions that a read fails before all rows, that its message is not empty, and that the release returns without a panic.

## Requirement Quality

#### [COMPLETENESS_GAP] FINDINGS
- Location: plan.md § Impact bullet 4; specs/_plans/add-streaming-result-sets/adbc-driver/ffi-statement-execution/spec.md § Scenarios
- Issue: plan.md states: "A driver-manager caller that runs another statement on the same connection before it reads a streaming reader to its end now interleaves that statement with the reader's fetches ... this plan does not specify that case." Before this plan, `execute` returned a reader whose rows were already in memory, so a later statement, COMMIT, or ROLLBACK on the connection could not affect it. After this plan, the outcome of that sequence is unknown. Impact bullet 3 still claims "The reader yields the same rows and schema as before." The plan has a local Exasol container (AGENTS.md § Testing), so it can establish the behavior by test instead of leaving it open.
- Fix: Run this sequence against the local container on both transports. Execute `multi_fetch_query` through the driver manager, read one batch, execute another query on a second statement of the same connection, run `COMMIT`, and read the rest. Then add a DELTA:NEW scenario to the ffi-statement-execution delta named "A statement on the same connection between reads of a streaming reader", with THEN steps that match the observed result. If the reader still works, the THEN steps state that it returns every remaining row exactly once. If it does not, they state that the read returns an error that carries the server message and that the release returns without a panic. Add a native test and a `_websocket` test to plan.md task 2.4 and the Scenario Coverage table. Replace Impact bullet 4 with the observed outcome.

#### [COMPLETENESS_GAP] FINDINGS
- Location: specs/_plans/add-streaming-result-sets/adbc-driver/ffi-statement-execution/spec.md § Scenario "Releasing a streaming reader before its end closes the result set handle"; specs/_plans/add-streaming-result-sets/query-execution/result-sets/spec.md § Scenario "Result set iterator closed before its end releases the result set handle"
- Issue: Two cases have no specified outcome. First, both GIVEN steps say the caller "has read some, but not all, batches". A release with no read at all is the common schema-probe pattern (execute, read the schema, release) that the Result Schema delta and ADR `zero-row-result-sets-carry-column-schema` address, and "some" does not clearly include zero batches. Second, no scenario covers a read or a release after the parent ADBC connection is released. `FfiConnection::drop` (src/adbc_ffi.rs L1410-1420) closes the transport. A later read therefore fails, where the in-memory reader used to return every row. plan.md § Impact does not list this change.
- Fix: In both scenarios, change the GIVEN step to "the caller has read no batch, or some but not all batches". Add a DELTA:NEW scenario to the ffi-statement-execution delta. GIVEN: a streaming reader whose connection the caller released before the reader's end. WHEN: the caller reads from the reader and then releases it. THEN: the read SHALL return an error and SHALL NOT return a batch, and the release SHALL return without a panic. Add a unit test for each change to plan.md task 2.1 and the Scenario Coverage table. Add the read-after-connection-release change to plan.md § Impact.

#### [ADR_CONFLICT] BLOCKER
- Location: plan.md § Implementation Tasks task 1.2 ("State in the doc comment that a `next_batch` future dropped before it completes abandons its fetch request"); decision-log.md § Design Decisions (no superseding entry)
- Issue: ADR `client-give-up-terminates-connection` decides: "Any client-side decision to give up on a running query MUST terminate the connection and MUST NOT abandon the in-flight request." ADR `server-enforced-query-timeout` names the failure: a future dropped mid-request "desynced the transport, left the `Connection` unusable". Task 1.2 makes that abandonment the documented contract of the new public async `next_batch`. The old blocking iterator could not be dropped mid-fetch. The new `next_batch` can be, through `tokio::time::timeout` or `tokio::select!`, which a streaming consumer often wraps around each read. After such a drop, the transport has sent `fetch_results` and not read its response, so the next request on the connection reads the stale response. Decision [2] cites this ADR for the FFI reader only, and no decision-log entry carries `Supersedes: client-give-up-terminates-connection`. The crate already conforms on the export timeout path: src/export/csv.rs L604 calls `TransportProtocol::terminate()`, and src/transport/lifecycle.rs L98-108 then returns a named error for every later operation.
- Fix: Conform to the ADR. In plan.md task 1.2, replace the doc-comment sentence with: "Hold the transport lock guard in a drop guard for the duration of `fetch_results` and `close_result_set`. If the `next_batch` or `close` future is dropped before the response is read, the guard calls `TransportProtocol::terminate()`, so every later operation on the connection fails with the terminated-transport error. Revise `terminated_error` in src/transport/lifecycle.rs so its text no longer names only the export." Add a DELTA:NEW scenario to the result-sets delta named "Dropping a next_batch call before it completes terminates the connection". GIVEN: a fetch request in progress. WHEN: the caller drops the `next_batch` future. THEN: the driver SHALL NOT send another request on that connection, and the next operation on the connection SHALL return an error that states the connection was terminated. Add a unit test to task 1.1 with a test double from src/transport/test_support.rs that keeps `fetch_results` pending, as the existing double keeps `execute_query` pending (L150-156). The test drops the future with `tokio::time::timeout` and asserts one `terminate` call. Add the row to Scenario Coverage. If the user wants abandonment instead, add a decision-log.md entry with `Supersedes: client-give-up-terminates-connection` and `Promotes to ADR: yes`.

#### [INFORMATION_COUPLING] FINDINGS
- Location: plan.md § Implementation Tasks tasks 1.2 and 1.3; decision-log.md § Design Decisions [1]
- Issue: After this plan, two functions each own the read loop of a result set. `fetch_all` owns `paginate_remaining`, the close, the ignored close error, and `check_buffered_rows`. `ResultSetIterator::next_batch` owns `fetch_page_after`, the close at the end, and the ignored close error. Decision [1] states "One owner of the close serves the Rust caller and the FFI reader", but `fetch_all` remains a second owner. The two already diverge. `fetch_all` runs `check_buffered_rows` on a result that needs no fetch and fails when the buffered rows differ from the total row count (src/query/results.rs L281, L364-376). Task 1.2 gives the iterator no such check. Task 2.3 moves FFI `execute` from `fetch_all` to the iterator, so the FFI path loses that check without a note.
- Fix: In plan.md task 1.3, implement `fetch_all` as `into_iterator` followed by a loop over `next_batch` that collects the batches. On an error, `fetch_all` awaits `close` and returns the error, as it does today. Delete `paginate_remaining` and add it to the Dead Code Removal table. In task 1.2, run `check_buffered_rows` in the first `next_batch` call when the result needs no fetch, so a buffered-row mismatch fails both paths. Add a unit test to task 1.1 for a result that needs no fetch and whose total row count differs from its buffered rows. Change decision-log.md [1] so it names the iterator as the only owner of the close.
