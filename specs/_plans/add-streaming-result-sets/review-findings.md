# Code Review Findings: add-streaming-result-sets

## Summary
- Files reviewed: 18
- Total findings: 7 (standard: 6, expert: 1)
- `cargo clippy --all-targets --all-features -- -D warnings` reports no issues on the working tree.
- The `InFlightRequest` termination on a panic (orchestrator point 2) is correct behavior and stays. A panic inside a fetch or close request leaves the response unread, and `tokio::sync::Mutex` does not poison, so a caught panic without termination would let the next request read a stale response. Production `terminate()` (`lifecycle::terminate`) does no I/O and cannot panic, so the guard cannot cause a double panic in production. Findings 2 and 3 below address the missing documentation and the test-side cost.
- Scenario tags (orchestrator point 3): every new test that implements a delta scenario carries a verbatim `/// Scenario:` line, and no changed file calls `std::env::set_var` or `std::env::remove_var`. The new inline comments state a reason in 1 or 2 lines, except the test comment covered by the expert finding.

## Standard fixes

### src/adbc_ffi.rs

#### [SENTINEL_ERROR_VALUE] The streaming reader falls back to an empty schema for an impossible state
- Location: line 1572-1576 (`StreamingRecordBatchReader::open`)
- Issue: `open` maps a `None` first batch to `Schema::empty()`. `ResultSet::into_iterator` always stores the execute response batch, and the first `next_batch` call returns it, so this branch never runs. If it ever ran, the reader would declare zero columns and then return batches that have columns, which breaks the reader schema contract silently instead of failing the execute.
- Fix: In src/adbc_ffi.rs `StreamingRecordBatchReader::open`, replace the `map_or_else(|| Arc::new(Schema::empty()), RecordBatch::schema)` fallback with `iterator.next_batch().await?.ok_or_else(|| QueryError::InvalidState("a result set iterator returns the execute response batch first".to_string()))?`, take `schema` from that batch with `first_batch.schema()`, and store `first_batch: Some(first_batch)`.

#### [UNTESTED_ERROR_PATH] The streaming reader tests accept any number of transport terminations
- Location: line 4714-4722 (`transport_answering`), used by every streaming reader test
- Issue: `transport_answering` sets `expect_terminate().return_const(())` with no call count, so that a failed mock expectation inside a request does not panic a second time in the `InFlightRequest` guard. As a result, no streaming reader test detects a termination on an ordinary error path. `streaming_reader_read_fails_with_fetch_error_message`, `streaming_reader_read_fails_on_row_count_mismatch`, `releasing_streaming_reader_before_end_closes_handle_without_fetch`, and `releasing_streaming_reader_ignores_a_failed_close` would all pass if the reader terminated the connection on a failed fetch or a failed close. The `ResultSetIterator` doc comment promises that the handle stays open after a failed fetch.
- Fix: In src/adbc_ffi.rs tests, change `transport_answering` to return the `MockTransport` together with an `Arc<AtomicUsize>` that a `expect_terminate().returning(...)` closure increments, as `count_closes` does for close requests, so the expectation still never panics. Update `query_transport` and every caller to take the counter, and in the four tests named above add `assert_eq!(terminations.load(Ordering::SeqCst), 0)` after the reader is dropped. Delete the two-line comment above the old `expect_terminate` call and put a one-line comment on the counter that states why it does not panic.

### src/query/results.rs

#### [MISSING_DESIGN_INTENT] The request guard does not state that a panic also terminates the transport
- Location: line 899-925 (`send_result_set_request`, `InFlightRequest`)
- Issue: The doc comments state that a dropped future terminates the transport. They do not state that a panic inside the request unwinds through the same guard and terminates the transport, or that this is intended because the response state is then unknown. They also do not state the constraint that the guard relies on: `TransportProtocol::terminate` must not panic, because a panic during unwinding aborts the process. Test authors meet this constraint only through the workaround comment in `src/adbc_ffi.rs` `transport_answering`.
- Fix: In src/query/results.rs, extend the doc comment of `InFlightRequest` with two sentences: a panic inside the request also drops the guard and terminates the transport, because the response state is then unknown; and `TransportProtocol::terminate` must not panic, because the guard can call it during unwinding, so a test double needs a non-panicking `terminate` expectation.

#### [IMPLEMENTATION_COUPLED_TEST] An end-of-stream test builds the iterator from its private fields
- Location: line 2750 (`test_next_batch_reports_exhausted_when_handle_was_already_released`)
- Issue: The test constructs `ResultSetIterator` with literal values for its private fields `handle`, `first_batch`, `rows_received`, and `complete`, so it breaks on any change to the iterator's internal state. The behavior it checks, that `next_batch` returns `None` without a request once the handle is closed, is already covered through the public API by `test_next_batch_closes_handle_at_end_and_ignores_close_error`, `test_next_batch_stops_at_total_rows_without_another_fetch`, and `test_close_after_end_sends_no_request`.
- Fix: In src/query/results.rs tests, delete `test_next_batch_reports_exhausted_when_handle_was_already_released`.

### tests/common/mod.rs

#### [TACTICAL_SHORTCUT] The dropped-fetch integration helper leaves one server session per run
- Location: line 904-907 (`assert_dropped_next_batch_terminates_connection`); callers tests/integration_tests.rs line 4045 and tests/websocket_integration_tests.rs line 2252
- Issue: The doc comment states that Exasol keeps the session of a client that disconnects during a fetch, so each run of `test_dropped_next_batch_terminates_connection` and `test_ws_dropped_next_batch_terminates_connection` leaves one session on the local database until it restarts. Repeated local runs accumulate these sessions, so the tests are not independent of earlier runs. The observation also contradicts the rationale of ADR `client-give-up-terminates-connection` ("The server session is released immediately"), and the comment is the only record of it.
- Fix: In tests/common/mod.rs, change `assert_dropped_next_batch_terminates_connection` to take `connect: impl Fn() -> F` instead of `connect: F`, call `open_iterator(connect(), multi_fetch_query())`, and record `let session_id = conn.session_id().to_string();` before the zero timeout. After `conn.close()`, open a second connection with `connect().await.expect("Failed to connect")`, run `execute_update(format!("KILL SESSION {session_id}"))` on it with `expect("the terminated session should be killable")`, and close it. Replace the last sentence of the doc comment with "Exasol keeps the session of a client that disconnects during a fetch, so the helper kills it from a second connection." Change the callers to `assert_dropped_next_batch_terminates_connection(get_test_connection)` in tests/integration_tests.rs and `assert_dropped_next_batch_terminates_connection(get_ws_connection)` in tests/websocket_integration_tests.rs.

### docs/queries.md

#### [OUTDATED_COMMENT] The termination rule is documented only for `next_batch`
- Location: docs/queries.md line 82; src/adbc/connection.rs line 695-713 (`Connection::query` doc comment); CHANGELOG.md `## 0.33.0` Breaking line
- Issue: `Connection::query` calls `fetch_all`, so dropping a `query` future while a fetch or close request awaits its response now terminates the connection. `query` is the entry point that docs/queries.md shows first. docs/queries.md names only `next_batch`, the `Connection::query` doc comment says nothing about it, and the CHANGELOG names `fetch_all` but not `query`. A caller that wraps `query` in `tokio::time::timeout` learns about the termination only from the error.
- Fix: In docs/queries.md line 82, replace "If you drop a `next_batch` future while it waits for Exasol" with "If you drop a `query`, `fetch_all`, `next_batch`, or `close` future while it waits for a fetch or close response from Exasol". In src/adbc/connection.rs, add to the `Connection::query` doc comment: "Dropping the returned future while a fetch or close request awaits its response terminates the connection; see [`ResultSetIterator::next_batch`](crate::query::ResultSetIterator::next_batch)." In CHANGELOG.md, change "Dropping a `next_batch`, `close`, or `fetch_all` future" to "Dropping a `Connection::query`, `fetch_all`, `next_batch`, or `close` future".

## Expert fixes

### src/adbc_ffi.rs

#### [INFORMATION_COUPLING] The streaming reader schema can differ from the batches it returns when the execute response has no rows
- Location: line 1553-1600 (`StreamingRecordBatchReader` doc comment, `open`, `next`); line 4956-4960 (`streaming_reader_schema_is_set_before_the_first_read` and its comment)
- Issue: The reader takes its schema from the execute response batch. When the execute response carries no rows, which is the case for large native results, `ResultSet::from_transport_result` builds that batch with `empty_record_batch` from the result set metadata schema, whose Arrow types come from `TypeMapper`. Every later batch goes through `with_field_metadata`, which keeps the Arrow types that the native decoder chose in `src/transport/native/result_parser.rs`. The reader therefore matches its batches only while `TypeMapper::exasol_to_arrow` and the native `fill_*_column` functions map every Exasol type to the same Arrow type. Today they agree for every type, because the native protocol always sends DECIMAL precision and scale. The agreement is not enforced anywhere, and two modules each own half of it. The `adbc-driver/result-schema` scenario requires every batch to carry the Arrow data types of the reader schema, and the Arrow C stream gives the consumer no per-batch schema, so a divergence would make the consumer read buffers with the wrong layout instead of failing. The struct doc comment states that the schema "carries the Arrow types the transport decoded", which is false for an execute response with no rows. Decision [3] rejects the metadata schema because a native batch "does not have to match `TypeMapper`", yet the reader uses the metadata schema in exactly that case. The unit test `streaming_reader_schema_is_set_before_the_first_read` proves the schema for an Int64 execute response batch, a type the native decoder never produces for DECIMAL(18,0), and no test covers a zero-row execute response followed by a fetch, so the tests pass over the inconsistent case.
- Fix: In src/adbc_ffi.rs `StreamingRecordBatchReader::next`, check every batch that `iterator.next_batch()` returns against `self.schema` before returning it: the field count, and for each field the name, `data_type()`, and `metadata()`. On the first difference, return `Some(Err(ArrowError::SchemaError(format!("column {name}: the reader schema has {expected:?}, but a fetched batch has {actual:?}"))))` and do not return the batch. Rewrite the struct doc comment to state that the schema is the schema of the execute response batch, which is the result set metadata schema when the execute response carries no rows, and that a read fails on a fetched batch whose field names, Arrow data types, or field metadata differ from it. Add the unit test `streaming_reader_read_fails_when_a_fetched_batch_differs_from_the_reader_schema` with `/// Scenario: Reader schema is available before the first read`: an execute response with zero rows, `Some(handle)`, and `total_rows` 1, one fetch that returns `ResultPayload::Arrow` with an Int64 `ID` column, a counted close; assert that the schema field is `Decimal128(18, 0)`, that the first read returns a zero-row batch, and that the second read returns `Some(Err(_))` whose message contains `ID`. In `streaming_reader_schema_is_set_before_the_first_read`, replace the comment with "Int64 stands in for a decoded type that differs from the metadata type, which the native decoder does not produce today."
