# Plan Review Findings: add-unit-test-coverage (round 1)

## Summary
- Axes checked: 6/6

## Premortem

Three failure stories drove the findings below.

**Story 1 — the number went green, the coverage did not.** CI reports 84 percent, the floor passes, and everyone believes unit coverage is solid. Most of the gain is the ~1,300 lines of new test code entering its own denominator. Production-only coverage moved from 57.5 to about 61 percent, not the committed 65. Nobody noticed, because no command in the plan measures production-only coverage. A decoder defect later ships in an untested `result_parser.rs` arm. Routes to [AMBIGUOUS_REQUIREMENT] (both instances).

**Story 2 — task 5.2 was declared done at 40 percent.** One task carried 250 of the 717 committed lines across ten unrelated areas of a 2,584-line file. The implementer covered the four metadata SQL builders, ran out of budget on `connect_with_transport` and `execute_statement`, and marked the task complete because "at least 250" was never decomposed into checkable pieces. The reported total still cleared 82 percent through test-code inflation, so no gate caught the shortfall. Routes to [TASK_GRANULARITY].

**Story 3 — the floor got deleted.** A later PR adds a 300-line module with no tests. The 82 percent overall floor still passes, but the Sonar new-code condition fails at 0 percent on changed lines. Because task 6.1 attaches `--fail-under-lines` to the step that produces `lcov-unit.info`, the next real regression skips the upload step, skips the `sonar` job, and leaves a required check permanently pending. The team removes the floor. Routes to [NFR_IGNORED] and [AMBIGUOUS_REQUIREMENT].

## Feasibility

- Issue: the stated fallback does not exist. Task 6.1 reads "if that flag combination is rejected, add a second `cargo llvm-cov report --lib --fail-under-lines 82` step that reuses the profile data". Running that command in this repo returns `error: --lib is specific to [test,nextest,nextest-archive,no subcommand] and not supported for subcommand 'report'`. The `report` subcommand rejects `--lib`, so the documented contingency is unimplementable. The primary form was verified to parse cleanly (`cargo llvm-cov --lib --lcov --output-path <p> --fail-under-lines 82` reaches crate selection with no flag-conflict error), but the plan never confirms the threshold is *evaluated* when the output format is lcov, and the code-quality/core delta makes that enforcement a MUST.
- Fix: In plan.md § Implementation Tasks task 6.1, replace the fallback sentence with: "if the threshold is not evaluated alongside `--lcov`, split the step into `cargo llvm-cov --lib --no-report` followed by `cargo llvm-cov report --lcov --output-path lcov-unit.info --fail-under-lines 82`" — drop `--lib` from the `report` invocation. Add a row to § Manual Testing that proves the primary form actually enforces: `cargo llvm-cov --lib --lcov --output-path /tmp/x.info --fail-under-lines 99; echo $?` expecting `1`.

## Requirement Quality

#### [AMBIGUOUS_REQUIREMENT] BLOCKER
- Location: plan.md § Requirements, row "Production-only coverage"; specs/_plans/add-unit-test-coverage/code-quality/core/spec.md § Scenario: Reported coverage figure records its composition
- Issue: the plan commits to "At least 65 percent, up from 57.49 percent, meaning at least 717 of the 4,058 uncovered production lines closed" and the spec delta makes it a MUST that "`AGENTS.md` MUST record the production-only line coverage measured for the same commit". No task, command, or checklist step measures production-only coverage. § Manual Testing and § Checklist contain only `cargo llvm-cov --lib` total-coverage commands. Worse, the plan rules out the only means of computing the figure: decision-log [2] states "`cargo-llvm-cov` offers no flag to exclude inline test modules, so stripping them needs custom tooling", and plan.md § Non-Goals lists "stripping test-module lines from the lcov file" as out of scope. The plan therefore states a hard numeric acceptance criterion that nothing in the plan can evaluate, and "the same commit" never names which commit. No pass/fail test can be written from either statement as it stands.
- Fix: Add a task to plan.md § Implementation Tasks group 6 that produces the figure — a `scripts/` helper that reads `lcov-unit.info`, subtracts the line ranges of each file's `#[cfg(test)]` module, and prints the production-only percentage — and add a § Manual Testing row invoking it with the expected value. In the code-quality/core delta, replace "measured for the same commit" with "measured on the merge commit of this plan by `scripts/<name>`". If the tooling stays out of scope, delete the "Production-only coverage" row from § Requirements and the corresponding `AND` clause from the delta, and demote 65 percent to a non-binding note in § Design.

#### [AMBIGUOUS_REQUIREMENT] BLOCKER
- Location: plan.md § Summary and § Impact; § Requirements, row "Reported coverage"; code-quality/core delta § Scenario: Unit test coverage floor enforced in CI
- Issue: the 82 percent reported target does not verify the plan's goal, because new test code enters its own denominator. Using the plan's own figures (15,215 of 19,486 covered; in-file test modules 9,941 lines at 97.9 percent covered), adding `T` lines of new test code and closing `P` production lines gives `P >= 763.5 - 0.159 * T`. The repo's existing ratio is 9,941 test lines per 5,487 covered production lines, or 1.81 test lines per covered production line. Closing the committed 717 lines implies `T` around 1,300, so 82 percent is reached at `P = 557`. Closing the full 1,371-line opportunity implies `T` around 2,480, so 82 percent is reached at `P = 369`. The floor therefore certifies 51 to 78 percent of the commitment, yet § Summary asserts the two are the same thing: "Raise library unit-test coverage from 78.1 percent to at least 82 percent ... closing at least 717 uncovered production lines". The durability claim fails the same way. At `P = 717`, `T = 1,300`, the post-change total is 17,205 of 20,786, or 82.77 percent, so a later PR can add about 195 fully-uncovered production lines and still clear 82 percent — while Sonar's new-code condition fails at 20 percent uncovered on changed lines. § Impact's "a future PR that adds production code without tests is blocked rather than merged" is false, and decision-log [3]'s margin rationale ("80 percent leaves no margin") reasons about the wrong metric.
- Fix: In plan.md § Summary, stop equating 82 percent with 717 lines — state the two criteria separately and name the denominator-inflation effect. In § Requirements, change the "Reported coverage" row to a floor derived from the projected post-change figure rather than 82, and add `--fail-under-file-lines` (verified available in this cargo-llvm-cov) as the per-file guard that actually blocks a new untested module. In § Impact, replace the "blocked rather than merged" sentence with the measured tolerance: "the total-coverage floor trips only after roughly 195 uncovered production lines accumulate; Sonar's new-code condition is the tighter guard." Add a § Consequences row recording that `cargo llvm-cov --lib` total coverage counts in-file test modules and so rises when test code is added.

#### [TACTICAL_SHORTCUT] ADVISORY
- Location: plan.md § Dead Code Removal, row `src/transport/native/handshake.rs:305-310`
- Issue: the removal is arithmetically justified but trades a graceful degradation for a panic, in the same function where the plan is removing a panic. Lines 305-310 are the whole `let block_data = if input_end <= interleaved.len() { ... } else { break };` expression; deleting the `else` arm leaves an unguarded `&interleaved[input_start..input_end]`. The unreachability claim holds — `num_blocks = floor(2 * L / 128)` so `num_blocks * 64 <= L` for any `L`, which is stronger than the plan's stated reason ("because `encoded_output_len` is a multiple of 128") — but the invariant lives 20 lines away at the rounding step (lines 277-279) with nothing linking the two, and no test can pin an unreachable branch. Any later change to the rounding turns a `break` into an index-out-of-bounds panic in a decoder parsing server-supplied bytes.
- Fix: In plan.md § Dead Code Removal, change the row to require replacing the branch with `debug_assert!(input_end <= interleaved.len(), "encoded_output_len rounding invariant broken");` above the direct slice, and correct the Reason column to the general argument: integer division makes `num_blocks * block_input_size <= interleaved.len()` hold for every input, not only for multiples of 128.
