## Premortem

Six months from now this plan failed. These are the likely reasons:

1. PR #89's implementation merges first. Its task 4.2 replaces the guard at the top of `execute_prepared_statement` with `self.lifecycle.require(...)` and edits the native test module. This PR changes the same function and the same test module, so the rebase conflicts in the file that the requester reserved for PR #89. The requester had split the files between two worktrees, and PR #89's plan says that `src/adbc/connection.rs` and `src/adbc_ffi.rs` "belong to another worktree and stay unchanged". The requester learns of the overlap at code review, after the implementation already ran. This story routes to `[INTENT_DRIFT]`.
2. A data engineer runs Python `executemany` with a very large numeric parameter list. The per-row loop was slow but finished. The new path holds three converted copies of the whole batch, and the process runs out of memory. Decision [8] made its headless choice on the claim that no call that succeeds today fails. This story routes to `[UNSTATED_ASSUMPTION]` (ADVISORY).
3. A later plan reads the recorded `adbc-driver/ffi-statement-execution` Background, which names the 64 MiB of one Docker image. A server that reports another size makes the Background false, although no scenario depends on the value. This story routes to `[IMPLEMENTATION_LEAKAGE]`.

## Feasibility

Checked without objection. Exasol 2025.2.1, the CI image, reports `maxDataMessageSize` 67,108,864, as 2026.1.0 does: the reviewer started that image on a scratch port and read the login info. The 64 MiB that tasks 4.11 and 4.12 assume therefore holds in CI, and a different size makes either test fail, not pass silently. Task 3.1 matches the code. `write_parameter_rows` writes the values row by row after the column headers, `infer_wire_type` falls back to the first value of a column when the handle has no parameter types, and `self.session` carries `max_data_message_size`. The wire-type test of task 3.3 can be built: a column `[Null, Number]` infers `T_CHAR` for the whole column and `T_DECIMAL` for a later range's first value, and `write_param_value` encodes both. With about 2,014 encoded bytes per row, task 4.12 puts row 42,000 in the second of three ranges, so the asserted stored ids hold.

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: decision-log.md § [8] Rationale ("No call that succeeds today fails"), § [8] Consequences, last bullet; plan.md § Impact, bullet "The memory use of a bound execution grows with the batch"; task 5.1
- Issue: Decision [8] settles its headless choice on "No call that succeeds today fails". This holds for the connection but not for memory. The per-row loop holds the converted parameters of one row. The new path holds three converted copies of the whole batch: the row-major `Parameter` rows of task 2.1, the column-major `serde_json::Value` data that `Connection::execute_batch_update` builds with `build_batch_parameters_data`, and the encoded rows of task 3.1. It also holds one range message of up to 64 MiB. Each `Parameter` and each `serde_json::Value` is an enum value, so a numeric column costs more per value than the 4 or 8 bytes it takes in Arrow. A large `executemany` that the per-row loop completes slowly today can run out of memory. The plan states that memory grows but not by how much, and it does not limit the claim that settles the choice.
- Fix: In decision-log.md § [8] Rationale, replace "No call that succeeds today fails" with "No batch that the per-row loop completes today breaks the connection". In § [8] Consequences and plan.md § Impact, name the three full-batch copies and the range message. In the docs text of task 5.1, state that a bound batch needs several times its Arrow size in driver memory, next to the existing pointer to `cursor.adbc_ingest`.

#### [REQUIREMENT_CONFLICT] ADVISORY

- Issue: The recorded scenario says that when Exasol returns a result set to a batch update, "the system MUST reject the outcome with an unexpected-result-set error". ## Design Depth

Checked without objection. No entry has `Promotes to ADR: yes`. `speq decision-log show` lists no ADR on message size or batch splitting. ADR-005 holds, because `Connection::execute_batch_update` keeps its arity check before the transport call. ADR-004 holds, because a row-count result has no columns. ADR `client-give-up-terminates-connection` does not apply: the split stops on a server error, not on a client give-up. The architecture delta follows the template. Its BASE equals `git hash-object specs/architecture.md` (`f88a7efd...`), it changes § Constraints by one bullet, and it copies the other 15 bullets verbatim. No § Components or § Data Flow line describes prepared execution, so the new bullet covers the rule. The native transport is the right owner of the encoded message size, and the split hides that size from `adbc_ffi` and `Connection`.
