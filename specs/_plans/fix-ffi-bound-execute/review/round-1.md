## Premortem

Six months from now this plan failed. These are the likely reasons:

1. A data engineer runs Python `executemany` with 2.5 million rows, or binds a large Arrow table to `cursor.execute`, over the default native transport. The driver sends the whole batch as one message. The server drops the TCP connection, so the session and its open transaction are lost. Before this plan, the same call was slow but succeeded. This story routes to `[UNSTATED_ASSUMPTION]` under Feasibility, and a reviewer probe reproduced it.
2. A later plan or a Rust API user relies on the recorded `prepared-statements/batch-execution` scenario, which promises a multi-row result-set batch in one execution. Exasol rejects it with 0A000. The new FFI Background states the opposite fact, and only the FFI adapter knows how to route around it. This story routes to `[REQUIREMENT_CONFLICT]` and `[INFORMATION_LEAKAGE]`.
3. The implementer cannot compile the C ABI test of task 3.2 because no dependency provides the Arrow C stream type. The lockfile check then fails because `libloading` joins the `exarrow-rs` entry. The implementer adds dependencies outside the plan, and the PR description required by `code-quality/dependencies` makes a false claim about the lockfile. This story routes to `[HIDDEN_DEPENDENCY]` and `[UNSTATED_ASSUMPTION]`.

## Feasibility

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: decision-log.md § [8]; plan.md § Context (bullet "Exasol behavior, probed against ..."), § Impact; adbc-driver/ffi-statement-execution/spec.md § "execute_update sends every bound row in one execution" and § "execute runs a row-count statement once for the whole bound batch"
- Issue: Decision [8] sends every bound row in one execution "whatever the number of rows". It rejects chunking "without evidence of a server limit", but its large-batch probe ran only over WebSocket: "The large-batch probe did not cover the native protocol." The FFI cdylib uses the native protocol by default. `build_execute_prepared_payload` in `src/transport/native/mod.rs` writes the whole batch as one message, with `total_rows` equal to `rows_in_msg`. A reviewer probe called `Connection::execute_batch_update` on the native transport against the local `exasol/docker-db` (2026.1.0). The table had the columns `DECIMAL(18,0)` and `VARCHAR(100)`, and each row carried a 40-character string, about 54 encoded bytes per row. 2,000,000 rows (about 108 MB) succeeded. 2,500,000 rows (about 135 MB) failed with `Failed to send message: Broken pipe (os error 32)`. The next query on the same connection failed with the same error. Above a payload of between about 108 MB and 135 MB, the server therefore drops the connection. The session is lost, and with autocommit off, which is the Python DB-API default, so is the open transaction. The per-row loop never sent a message this large, so a large `executemany` or bound Arrow table that is slow today would fail and kill the connection. Both scenarios require one execution for "one or more rows" with no upper bound, and the default transport cannot meet that. Escalation is HUMAN because every remedy changes what the feature does for a user or crosses a user constraint. Chunking in `src/adbc_ffi.rs` gives up the all-or-nothing rule of decision [4] under autocommit. Rejecting an oversize batch before sending turns a call that works today into an error. Sending one execution as several data messages, for which the message header has separate `total_rows` and `rows_in_msg` fields, changes `src/transport/native/mod.rs`, which the user reserved for PR #89.
- Fix: Ask the requester to choose the behavior for a native-protocol bound batch whose encoded parameters exceed the server's data message size. The options are chunking in `src/adbc_ffi.rs`, rejecting the batch before sending, or a multi-message execution in the native transport after PR #89 merges. Then rewrite decision-log.md § [8] with the native probe result above and the chosen behavior. Add a scenario to adbc-driver/ffi-statement-execution/spec.md that states what `execute_update` and `execute` do for such a batch: the error status, whether the connection stays usable, and which rows are stored. Add an integration test for it to tests/driver_manager_tests.rs and a row to plan.md § Scenario Coverage. In plan.md § Context, name the WebSocket transport in the "3,000,000-row batch" claim, and state the limit in § Impact and in the docs text of task 4.1.
- Escalation: HUMAN

#### [HIDDEN_DEPENDENCY] BLOCKER
- Location: plan.md § Implementation Tasks 1.1 and 3.2, § Dependencies; decision-log.md § [7]
- Issue: Task 3.2 calls `StatementExecuteQuery` "with a result stream" and then releases the stream. The adbc_ffi 0.24 function type `FuncStatementExecuteQuery` takes a `*mut arrow_array::ffi_stream::FFI_ArrowArrayStream`. The crate reaches Arrow only through `arrow = "58"` with default features, and `arrow::ffi_stream` exists only under Arrow's `ffi` feature. Neither `src/` nor `tests/` uses it today. A reviewer applied task 1.1's Cargo.toml edits to a scratch copy and compiled a test that uses `arrow::ffi_stream::FFI_ArrowArrayStream::empty()`. It failed with `could not find ffi_stream in arrow`. Task 1.1 lists only `adbc_ffi` and `libloading` "for task 3.2", and decision [7] states "no new crate enters the dependency tree". Neither names the dependency that provides the stream type.
- Fix: In plan.md task 1.1, add `arrow = { version = "58", features = ["ffi"] }` under `[dev-dependencies]`. It adds no package to Cargo.lock, because `adbc_ffi` already builds `arrow-array` with `ffi`. In task 3.2, name `arrow::ffi_stream::FFI_ArrowArrayStream` as the stream type. Add the dev-dependency feature to plan.md § Dependencies and to the Decision line of decision-log.md § [7].
- Escalation: MECHANICAL

## Requirement Quality

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: adbc-driver/ffi-statement-execution/spec.md § Background; recorded specs/prepared-statements/batch-execution/spec.md § "Batch query execution returning a result set"
- Issue: The new Background says: "Exasol rejects a multi-row parameter set for a statement that returns a result set". Decision [2] records the 0A000 probe behind it. The recorded scenario says the opposite: "GIVEN a prepared statement and multiple rows of bound parameter values / WHEN the batch is executed for a result set / THEN the system SHALL send all rows to Exasol in a single prepared-statement execution / AND the system SHALL return the result set in Arrow form". Both cannot hold. A reviewer probe confirmed the rejection on the native transport as well. `Connection::execute_batch` with two rows for `SELECT a FROM t WHERE a = ?` failed with `Feature not supported: Prepared statement with multiple result tables (SQL state: 0A000)`. The plan cites `batch-execution` in plan.md § Context bullet 14 but leaves the false requirement in the library. After `/speq:record`, the library holds two contradictory statements about the same Exasol call. The only test of that scenario is `test_execute_batch_select_single_row`, which binds one row.
- Fix: Add specs/_plans/fix-ffi-bound-execute/prepared-statements/batch-execution/spec.md with a `DELTA:CHANGED` block for "Batch query execution returning a result set". Its GIVEN reads "a prepared statement that returns a result set and one row of bound parameter values". Add the feature to plan.md § Features, and add a § Scenario Coverage row that maps the scenario to `test_execute_batch_select_single_row`. In decision-log.md § [2] Consequences, state that `Connection::execute_batch` passes the Exasol 0A000 error through for two or more rows of a result-set statement. If you instead add a scenario for the multi-row rejection, put its test outside tests/integration_tests.rs, or record the overlap with PR #89 in decision-log.md § [11].
- Escalation: MECHANICAL

#### [COMPLETENESS_GAP] ADVISORY
- Location: adbc-driver/ffi-statement-execution/spec.md § Scenarios; decision-log.md § [1] Consequences and § [2] Consequences
- Issue: The plan describes two error paths of a bound batch but specifies neither. Decision [1] says that a bound batch with the wrong column count "fails with a parameter binding error before any transport call" (ADR-005). `to_adbc_error` reports that error with status `Internal`. Decision [2] says that `execute_update` on a result-set statement with bound rows fails, with `UnexpectedResultSet` for one row and Exasol 0A000 for two or more. No scenario in the new feature states either behavior, and no task tests them through the FFI. A wrong-width parameter tuple and Python `executemany("SELECT ...", rows)` reach these paths.
- Fix: Add the scenario "A bound batch with the wrong column count fails before execution" to adbc-driver/ffi-statement-execution/spec.md, and state the error status and that no execution request is sent. Add a unit test for it to task 2.5, with `execute_prepared_statement` expected `.never()`. Optionally, add a scenario stating that `execute_update` with a bound batch fails for a statement that returns a result set.

## Design Depth

#### [INFORMATION_LEAKAGE] ADVISORY
- Location: decision-log.md § [2]; plan.md task 2.3
- Issue: Exasol cannot run a multi-row parameter set for a statement that returns a result set. The plan puts this constraint in the FFI adapter: `execute_bound_batch` routes by `handle_ref().result_columns`. `Connection::execute_batch`, the module that talks to Exasol, still accepts a multi-row result-set batch and fails, and its doc comment says "Use this for batch SELECT statements". A Rust API caller and an FFI caller get different results for the same input. Any future caller of `execute_batch` must learn the rule again. The user's constraint covers only the login path of `src/adbc/connection.rs`, so moving the routing into `Connection::execute_batch` was allowed. Decision [11] chose not to do it, probably to avoid conflicts with PR #89, but no entry states that tradeoff or schedules a follow-up.
- Fix: In decision-log.md § [2], add an Alternatives line for "route inside `Connection::execute_batch`" with the reason it lost, which is the merge risk with PR #89. Add a Consequences bullet that records a follow-up issue to move the routing into `Connection::execute_batch` after PR #89 merges.

#### [TACTICAL_SHORTCUT] ADVISORY
- Location: decision-log.md § [6]
- Issue: The Decision text of ADR-003 names "`adbc_core` lifting the `arrow-schema <59` cap" as its trigger, and its Consequences say "The maintainer removes the suppression and retries `cargo update` when the trigger fires." This plan fires that trigger and keeps the suppression. The trigger that now applies lives only in `deny.toml` and the `code-quality/dependencies` spec. Decision [6] rejects a superseding ADR. A later reader of ADR-003 will therefore find a trigger that has fired and a suppression that was not removed. The mismatch existed before this plan, but this plan is the change that makes it visible.
- Fix: Decide in decision-log.md § [6] whether to add a superseding entry (`Supersedes: suppress-ghsa-2f9f-gq7v-9h6m-via-deny-toml`, `Promotes to ADR: yes`, Rationale naming rule-2 criterion 3 and the `speq decision-log show` result) that restates the trigger as the move to arrow and parquet 59. If you keep `no`, add a Consequences bullet stating that ADR-003's named trigger no longer applies and that `deny.toml` holds the operative trigger.
