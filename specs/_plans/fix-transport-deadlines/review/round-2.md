## Premortem

Six months from now this plan failed. Three ways it got there:

1. A contributor adds a TLS option, for example a custom root store, to the native transport. The WebSocket transport keeps the old behavior, because task 5.1 wrote a second copy of the same rustls configuration and handshake step. The user had asked for no duplicated code between the two transports. Routed to `[SCOPE_REDUCTION]`.
2. `/speq:record` merges the architecture delta. The constraint "The native transport fetches up to the server's maximum data message size per batch" ends up glued to the end of the tunnel bullet, and a later delta that rewrites the tunnel bullet deletes it without anyone noticing. Routed to `[ARCHITECTURE_DRIFT]`.
3. The follow-up ties the tunnel bound to the connection timeout and amends the one scenario that decision [9] names. The `csv-export-timeout` Background, the architecture, and three doc texts still say 30 seconds. In the same release, a user with `?query_timeout=60` and a schema in the URI connects through a proxy that stalls after login, and `Connection::from_params` hangs although the docs promise that a silent server fails within the connection timeout. Routed to `[INFORMATION_LEAKAGE]` and `[COMPLETENESS_GAP]`.

## Feasibility

Checked without objection, apart from the finding below. The `LifecycleSteps` design is buildable against the real code as specified:
- `TransportProtocol` is `#[async_trait]` with `Send + Sync` (`src/transport/protocol.rs:144-145`), and `async-trait = "0.1"` is a dependency (`Cargo.toml:45`). A crate-private `#[async_trait]` trait with a `Send` bound therefore returns boxed `Send` futures that the transports' `async_trait` impls can await.
- `authenticate(&mut self, credentials: &Credentials)` (`native/mod.rs:832`, `websocket.rs:483`) matches `login_exchange(&mut self, &Credentials)`. `authenticate_within_deadline` copies the `Copy` deadline out of the lifecycle before the login future borrows the transport mutably. It calls the release step and records the state only after `timeout_at` has completed or dropped that future, so no borrows overlap.
- `fn terminate(&mut self)` is synchronous (`protocol.rs:293`), and so is `release_connection`, so the shared `terminate` adds no await to the trait method.
- Every guard that tasks 4.2 and 5.2 replace compares against exactly one state: `Authenticated` for the eight operations, `Connected` for login, and `Disconnected` for connect. `require(expected, message)` expresses each one with its current message.
- Both `close()` bodies return early for `Disconnected` and `Closed`, ignore the errors of the disconnect I/O, and end in `terminate()` (`native/mod.rs:1197-1211`, `websocket.rs:735-773`). `close_gracefully` with a `send_disconnect` that returns `()` reproduces that sequence.
- The tests that read or write `state` (`native/mod.rs:1281-1326`; `websocket.rs:825-975`, `1393-1455`, and `authenticated_transport` at `1513`) can use `ConnectionLifecycle::in_state`, because it sets any state and no such test depends on a stored deadline.
- `test_export_to_callback_arms_no_timer_when_the_deadline_is_left_unset` builds its options with `use_tls(false)` (`src/export/csv.rs:911-916`). Its tunnel setup therefore completes before the clock is paused and advanced 600 seconds, and the 30-second tunnel deadline cannot fire in it. It is the only paused-clock test in `src` and `tests`.

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: plan.md task 5.1
- Issue: Task 5.1 does not say how a failure that is not a timeout maps in the new WebSocket TCP connect and TLS handshake steps. Today every failure of `connect_async_tls_with_config`, including a refused connection, a TLS failure, and a rejected upgrade, becomes `TransportError::WebSocketError` (`websocket.rs:475`). After the split, an implementer can map the TCP connect to `IoError` and the TLS handshake to `TlsError`, as the native transport does (`native/mod.rs:783` and `:820`), or keep `WebSocketError`. Task 4.1 says "keeping today's error mapping", but task 5.1 has no such sentence. The variant that a direct `TransportProtocol` caller sees on a refused connection can therefore change without a changelog line. No test in `src` or `tests` asserts `WebSocketError` today.
- Fix: In task 5.1, state the mapping for each step: `TcpStream::connect` failures as `TransportError::WebSocketError(e.to_string())` as today, TLS failures as `TransportError::TlsError`, and upgrade failures as `TransportError::WebSocketError`. If any variant changes for a failure that is not a timeout, add a `Changed:` line to task 7.3.

## Requirement Quality

#### [COMPLETENESS_GAP] ADVISORY
- Location: connection-management/connection-timeout/spec.md § feature description; plan.md § Impact (first bullet); plan.md tasks 7.1 and 7.3
- Issue: The description says "The connection timeout limits how long opening a connection to Exasol may take" and "A server, proxy, or load balancer that accepts the TCP connection and then stops answering fails the connection within that limit instead of blocking the caller." That holds only until the login ends. After the login, `connect_with_transport` calls `set_query_timeout` when a query timeout is configured (`src/adbc/connection.rs:210-219`), and `from_params` runs `OPEN SCHEMA` through `set_schema` when the URI names a schema (`:270-271`). Neither call runs under the deadline, and the plan leaves that file unchanged. A server that stops answering after the login therefore still blocks `Connection::from_params` for such a URI. § Impact, the `docs/setup-and-connect.md` paragraph of task 7.1, and the changelog line of task 7.3 repeat the broader claim.
- Fix: In the feature description, § Impact, task 7.1, and task 7.3, state that a server that stops answering during the TCP connect, the TLS handshake, the WebSocket upgrade, or the login fails the connection within the limit. Add one sentence to the description and to the task 7.1 paragraph: the connection timeout does not bound the session setup after the login, which sets the `queryTimeout` attribute and runs `OPEN SCHEMA` for a URI schema.

#### [AMBIGUOUS_REQUIREMENT] ADVISORY
- Location: connection-management/session-and-lifecycle/spec.md § "Terminate a connection whose in-flight response is no longer trusted" (third step) and § "Operations after an export timeout name the termination" (WHEN and THEN); plan.md task 2.3
- Issue: Both scenarios say that every operation other than `close` fails. `is_connected()` returns a `bool` and `terminate()` returns `()`, so neither can fail. The new scenario's THEN step "the operation SHALL fail with an error" cannot be met by a second `terminate()` call. The plan's tests already follow the intended reading: they assert that `is_connected()` is false and do not test a second `terminate()`. The defect is in the wording only.
- Fix: In both scenarios, replace "operation ... other than `close`" with "operation that sends or awaits a protocol message (connect, authenticate, and every statement, fetch, result-set, prepared-statement, and attribute operation)". Apply the same wording to the task 2.3 doc text "every other operation fails with the terminated-transport error".

#### [PROSE_UNCLEAR] ADVISORY
- Location: plan.md task 2.1 (the doc comment of the terminated-error function) and task 2.2; decision-log.md entries [7] and [8]
- Issue: The name `terminate` refers to two things: the trait method `TransportProtocol::terminate()` and the new shared function `lifecycle::terminate`. Task 2.1's doc comment states that "the export timeout is the only caller of `terminate()` apart from `close()`". After this plan, `close()` no longer calls the trait method, because it runs `close_gracefully`. The login timeout in `authenticate_within_deadline` also calls the shared function. The statement is therefore false under both readings. The invariant the plan relies on is narrower: only `TransportProtocol::terminate()` leaves the state `Terminated`, because the login timeout and `close_gracefully` record `Closed` afterwards, and `export_to_callback` is the only caller of `TransportProtocol::terminate()`.
- Fix: In task 2.1 and in decision [7] Alternatives (b) and Consequences, replace the sentence with: "Only `TransportProtocol::terminate()` leaves the transport `Terminated`, and `export_to_callback` is its only caller. The login timeout and `close()` run the shared release and then record `Closed`." In tasks 2.2 and 4.2 and decision [8], write "the shared `terminate` function" every time the text means `lifecycle::terminate`.
