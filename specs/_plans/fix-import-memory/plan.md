# Plan: fix-import-memory

## Summary

The CSV conversion path of Parquet import and the multi-file CSV import send data through the HTTP tunnel while they read it, so their memory use no longer grows with the size of the input. The docs state that `import_from_parquet_stream` buffers its whole input and name the alternatives with their real memory behavior.

## Context

- Issue #69 lists import paths that hold more data in memory than they need. This plan covers items 1, 3, and 4 of #69. Item 2 (serve native Parquet from the file on disk) needs an amendment of the parquet-io scenario that requires a whole-file buffer, and goes to a later plan.
- Item 1: on the CSV conversion path, `parquet_to_csv_bytes` (`src/import/parquet.rs:306`) renders the CSV of the whole Parquet file into one `Vec<u8>` before the tunnel opens, and `stream_csv_bytes` (`src/import/parquet.rs:364`) then re-chunks that buffer. The multi-file fallback `convert_parquet_files_to_csv` (`src/import/parallel.rs:435`, CSV loop at `:481`) does the same for every file before `ParallelTransportPool::connect`.
- Item 3: `csv::import_from_files` (`src/import/csv.rs:526-545`) reads and compresses every file in full before it connects.
- Item 4: native Parquet import buffers the raw Parquet bytes, as parquet-io requires ("Native Parquet import on Exasol 2025.1.11+", "Import Parquet from stream"). This plan keeps that buffer and documents it.
- `import_from_record_batches` and `import_from_arrow_ipc` (`src/import/arrow.rs:622`, `:670`) also build their whole CSV in memory before they send it. Decision [3] covers how the docs name them. Issue #69 item 4 calls both functions streaming alternatives, but the code shows that neither streams: `src/import/arrow.rs:634` builds one CSV buffer for all batches, and `:686` reads the whole IPC input before it parses it. The docs therefore name `import_from_arrow_ipc` as a function that reads its whole input.
- `exarrow_rs::import::parallel` is a public module (`src/import/mod.rs:42`), so `convert_parquet_files_to_csv` and `stream_files_parallel` are public API. This plan changes no public signature and no wire protocol, so it ships as patch release 0.21.4. PR #95 carries the 0.22.0 release separately, and this plan does not modify it.
- A row-less Parquet file returns 0 without a connection today (`test_import_from_parquet_returns_zero_for_a_row_less_file`, `test_import_from_parquet_stream_returns_zero_for_a_row_less_file`). The streaming paths keep this by reading the row count from the Parquet metadata.
- Assumption: Exasol fails an IMPORT statement as a whole when a tunnel body ends without the terminating chunk, the zero-length chunk that ends a chunked HTTP body. `import_csv_internal` already relies on this (`src/import/csv.rs:813-815`). The integration tests for the two "imports no rows" scenarios check it on `exasol/docker-db:2025.2.1` only, with the CSV path forced. The CSV path is the default only on servers below 2025.1.11, so a Manual Testing row runs the same check against an 8.x image.
- Assumption: Exasol sends the GET requests for all files of one IMPORT without waiting for an earlier file to finish. Decision [2] and the recorded parallel-import scenario "Parquet conversion is parallelized" depend on this, because each file's conversion now starts only when its connection receives a GET. No test in this repository checks the server side. The unit test in task 1.6 checks the driver side: when the GETs arrive at the same time, both producers run at the same time.
- Assumption: the synchronous Parquet reader of the `parquet` 58 crate reads the column chunks of a row group only when it reaches that row group. The unit test in task 1.2 depends on this. If the reader prefetches one row group, the test still holds, because it checks the last of 8 row groups.
- Architecture: no change. `specs/architecture.md` § Components already describes the import component as converting non-CSV input to CSV while streaming. This plan makes the CSV paths match that description.
- Follow-up plans:
  - `seekable-native-parquet-import`: serve native Parquet range requests from the file on disk instead of a whole-file buffer (#69 item 2, amends parquet-io).
  - `stream-single-input-import`: stream `import_csv_from_file`, `import_csv_from_stream`, `import_csv_from_iter`, `import_csv_from_callback`, `import_from_record_batches`, and `import_from_arrow_ipc`, which still read their whole input into memory.
  - `remove-parallel-buffer-api`: remove the public `convert_parquet_files_to_csv` and `stream_files_parallel` at the next minor release, since no import path calls them after this plan.

## Impact

- No breaking change. Public signatures, IMPORT SQL, and the tunnel wire format stay the same.
- Memory: on the CSV conversion path, `import_from_parquet` and `import_parquet_from_files` hold a few RecordBatches of CSV per file instead of the CSV of every file. `import_from_parquet_stream` still holds the whole Parquet input but no longer the whole CSV. `import_csv_from_files` with two or more files holds a 64 KiB piece per file instead of every file, plus the encoder state per file when compression is set: an estimated few hundred KB for gzip and an estimated 5 MB for bzip2 at its default level 6. The memory per file of the Parquet paths scales with `ParquetImportOptions::with_batch_size`.
- Error timing: a value that fails CSV conversion now fails the import after Exasol has started the IMPORT statement. Before, the import failed before any IMPORT ran. The error variant stays `ImportError::ConversionError`, and the target table receives no rows. Exasol now records a failed IMPORT statement for such an import.
- Error timing: in `import_csv_from_files`, a read error after a file opens, such as an I/O error partway through a file or a path that names a directory, now fails the import with `ImportError::ParallelImportError` after the IMPORT starts. The message names the stream index and the file path. Before, the read failed with `ImportError::IoError` before any connection opened.
- `import_csv_from_files` with one file, `import_csv_from_file`, and the native Parquet paths keep reading their whole input into memory. The docs state this.
